# 難易度の客観化と出題頻度のデータ化（設計）

`qa/questions.json` の `difficulty`（Lv1〜4）は、いま**書き手の感覚**で付いている。
TAXONOMY §2 は客観化の基準として「市販問題集のどのレベルで問われるか ＋ 出題頻度」を挙げているが、
その**実データがまだ無い**。ここではその2つを埋める設計を決める。

出典は `C:\Users\maequ\マイドライブ\化学\問題集`。解析の枠組みは既に
`問題集/_解析/`（索引 `index.json` 6527行/4936大問・手筋 `db/moves.json` 40件・
問題DB `db/problems.jsonl`）にある。**これを作り直さず、qa 側から参照する**。

---

## 1. 何に何を使うか（役割分担）

| 欲しいもの | 出典 | なぜそれか |
|---|---|---|
| **Lv の根拠**（暗記必須度・受験の階層） | **セミナー化学＋化学基礎**（傍用問題集） | レベル区分が**本の構造として与えられている**（基本例題／基本問題／発展例題／発展問題）。教科書傍用なので**網羅的**で、学校採用の標準。「どこまでが標準か」の線引きにそのまま使える |
| **出題頻度**（志望校別の優先度） | **全国大学入試問題正解 化学 12巻**（2010〜2021入試） | 既に `_解析/index.json` として機械可読になっている。母集団が4936大問と大きい |
| 解法の手筋との対応 | `_解析/db/moves.json` | qa の知識項目と手筋は**別物**（知識 vs 手続き）。将来 `req` で結ぶ余地を残す |

**なぜセミナーか**: 難易度を「難しさ」ではなく**受験での位置づけ**で決めるという TAXONOMY の方針に、
傍用問題集のレベル区分が直接対応する。重要問題集や新演習は**上位層に寄っている**ので、
Lv1〜2（生存・標準）の線引きに使えない。版が古い可能性はあるが、
**傍用の基本／発展の区分は改訂で大きく動かない**ので Lv の根拠としては安定する。

## 2. 著作権の扱い（`_解析/SCHEMA_問題DB.md` と同じ規則）

- **問題文・解説文は一切転記しない。**
- 記録するのは「**どのレベル区分に、この知識項目を問う問題があるか**」という**事実メタデータ**だけ。
  これは統計であって著作物の複製ではない（TAXONOMY §2 の Lv 割り当て基準・§2.7 と同じ原則）。
- 公開するのは**集計結果**（Lv の分布・頻度）であって、対応表の元データではない。
- 問題番号は記録してよい（事実）。**設問の中身は書かない。**

## 3. データの形

### 3-1. `questions.json` の各項目に足すフィールド

```json
{
  "code": "org.carbonyl.silver-mirror",
  "difficulty": 2,
  "source": {
    "seminar": { "level": "基本問題", "items": [412, 415], "edition": "2026-08 時点の所蔵版" }
  },
  "freq": {
    "tier": { "kyotsu": 0, "nan_kokkoritsu": 0, "kokkoritsu": 0, "nan_shiritsu": 0, "shiritsu": 0 },
    "univ": {}
  }
}
```

- `source.seminar.level` … `基本例題` / `基本問題` / `発展例題` / `発展問題` のいずれか。
  **複数レベルに出るときは最も低いほう**を採る（＝「どこから必要になるか」を見る）
- `source.seminar.items` … 問題番号の配列（事実。中身は書かない）
- `freq` … TAXONOMY §2.7 で予約済みの形。**今回は器だけ用意し、値は第2段で埋める**
- どちらも**任意フィールド**。無くても動くことをテストで保証する

### 3-2. Lv とセミナーのレベル区分の対応

~~初期案（4区分を Lv1〜4 に一列に並べる）~~ → **21章の実データで作り直した**（2026-08-06・下の §3-3）。

| セミナーでの登場のしかた | 言えること | 信号の強さ |
|---|---|---|
| **基本**（基本例題・基本問題）に出る | **Lv ≤ 2** | 強い |
| **発展にだけ**出る（基本に一度も出ない） | **Lv ≥ 3** | 弱い |
| **どこにも出ない** | **何も言えない** | — |

判定は `node qa/tools/verify_seminar_map.js` が出す。章ファイルを glob で拾うので、
章が増えても検査対象に入れ忘れる事故が起きない。

### 3-3. 初期案が壊れた2点（21章の実データ・2026-08-06）

**(a) 出題は上限しか語らない。** 「基本問題に出た＝Lv2」とすると、Lv1 の基礎事実
（`org.ali.formula-alkene` など）が全部 Lv2 に上がってしまう。**Lv1 の事実は基本にも発展にも出る**。
だから両側検定にすると食い違いが 45%（15/33件）に膨らみ、信号として使えなかった。
片側（上限）だけにすると 15%（5/33件）に落ちる。

**(b) 例題と問題の別は難易度ではなく役割の別**（解法提示か演習か）。
初出区分ごとに現行 Lv を集計すると、**基本例題 {Lv1:3, Lv2:5, Lv3:1} と
基本問題 {Lv1:5, Lv2:13, Lv3:1, Lv4:1} がほぼ同じ分布**になる。
とくに「基本例題44」は7コードにまたがる総まとめ例題で、Lv1（生存）ではありえない。
→ **セミナーの解像度は 基本／発展 の2値**。これが §7 未決事項2 の答え。

**(c) 未登場を Lv4 の根拠にしてはいけない。** 21章では **Lv1 の18項目中10項目が未登場**だった
（`alkane-bp` / `alkane-state` / `alkene-functional` など）。セミナーは**要項（まとめ）に
書いた事実を問題にしない**ので、基礎事実がそのまま落ちる。「傍用にすら無い」と
「要項にあるが問題にならない」は別で、区別には入試側のデータが要る。
初期案の最下段（どこにも出ない → Lv4 または範囲外）は**逆向きに壊れる**ので削除した。

### 3-4. 未登場の中身が分かった（20・21章の2章で・2026-08-06）

20章を入れて、**未登場コードが何の知識なのか**を数えられるようになった。
2章の担当単元（`anal` ＋ `aliphatic`・81項目）で未登場は36件。その内訳:

| 種類 | 件数 | 例 |
|---|--:|---|
| **性質・分類・定義** | 16 | `class-aliphatic` / `alkane-bp` / `alkane-state` / `alkene-functional` |
| **検出・操作** | 7 | `detect-c` / `detect-h` / `detect-n` / `qualitative-def` |
| **命名** | 5 | `suffix` / `name-mainchain` / `name-numbering` |
| その他（個別の反応・製法） | 8 | `keto-enol` / `vinylchloride-prep` / `meso` |

**28 / 36 が「定義・分類・性質・命名・検出」**。どれも傍用が**要項に書いて問題にはしない**型で、
**難しさとは無関係**（`class-aliphatic` や `alkane-state` は Lv1 の生存知識）。
§3-3 (c) の裏づけがこれで取れた。

> **命名は1件も出てこなかった。** 20章（有機化合物の特徴と構造）に集まると予想して
> 20章を先に読ませたが、**回収できたのは異性体・キラリティ側の5件だけ**で、
> IUPAC 命名の5件（`suffix` / `name-*`）は2章を通して0件だった。
> 命名は傍用では**要項の表**で扱われ、独立した問題にならないと見るのが妥当。
> → 残り6章でも命名・検出コードは出てこない見込みなので、**出てこないことを異常と扱わない**。

### 3-5. ⚠ Lv に「起草順の水増し」が見つかった（22章まで・2026-08-06）

22章（alcohol ＋ carbonyl ＋ fat）を入れたら、**食い違いが 15% → 25% に跳ねた**。
下げ候補が3→20件で、しかも**単元ごとに固まって出る**。

**単元ごとに固まるのは系統誤差の印**なので、起草順と平均 Lv を照らした。**一致した。**

| 起草日 | 単元 | n | 平均 Lv |
|---|---|--:|--:|
| 2026-07-30 | aliphatic | 66 | **2.02** |
| 2026-07-30 | anal | 15 | 2.20 |
| 2026-07-30 | alcohol | 19 | 2.26 |
| 2026-08-05 | carbonyl | 37 | 2.32 |
| 2026-08-05 | aro | 22 | 2.50 |
| 2026-08-05 | phenol | 15 | 2.60 |

| 2026-08-05 | fat | 15 | **2.80** |
| 2026-08-05 | bio | 44 | 2.52 |
| 2026-08-05 | poly | 34 | 2.68 |

**最初に丁寧に作った3単元（07-30）が 2.0〜2.3 で、量産した 08-05 の並びが 2.3 → 2.8 へ単調に上がる。**
Lv が**実際の難しさではなく、いつ書いたかと相関している**。主観で連続して難易度を付けるときの
典型的な水増しで、TAXONOMY §2 が「セミナーで客観化する」と決めていたのはまさにこれを潰すため。

**セミナーの側が正しい**ことは自分でも確かめた。`org.fat.micelle`（ミセルの向き）は
教科書本文の図で出るのに Lv3「受験標準」、`org.fat.drying-oil`（乾性油）は
ヨウ素価と一緒に必ず出るのに **Lv4「難関」**。どちらも重すぎる。

#### だから個別に直さない —— 23章で仮説を試す

fat の7件をいま下げても、**同じ水増しを持つ aro・phenol・aroN・bio・poly（未測定）が残る**。
潰すべきは項目ではなく**列そのもの**なので、23章（aro ＋ phenol ＋ aroN）を待つ。

> **予測（23章で判定できる）**: 水増しが起草順由来なら、平均 Lv 2.50 / 2.60 / 2.69 の
> **aro・phenol・aroN は fat に近い高い食い違い率（おおむね 40〜55%・下げ側に偏る）を示す**。
> - **予測どおりなら** → 単元ごとの一括補正（列の再校正）を行う
> - **これらが 15% 程度に収まるなら** → 水増しは fat 固有で、起草順は偶然の相関。
>   その場合は fat だけを直す
>
> ⚠ **「8章そろうまで待つ」を理由に据えるのは、もうやめる。** 22章の時点で
> anal・aliphatic・alcohol・carbonyl・fat の5単元は**測り終わっている**
> （§6-2 の対応表どおり、これらは22章以降に出てこない）。未登場は情報なし（§3-3 c）なので、
> 待っても増えない。**23章を待つ理由は「仮説の判定に要るから」**であって、
> 網羅を待っているのではない。

## 4. 対応づけの単位をどうするか（最大の設計判断）

qa の知識項目は **283個**、セミナーの問題は**1問が複数の知識項目にまたがる**。
入試問題正解の索引は**分野レベル**（「脂肪族化合物の反応」674件）までしか持たず、
qa のコード単位とは粒度が3段ほど違う。

したがって **問題 → コードの多対多**になる。対応表は別ファイルに切り出す:

```
qa/data/seminar_map.jsonl     1行 = { "item": 412, "level": "基本問題", "codes": ["org.carbonyl.silver-mirror", ...] }
```

**questions.json に直接書かない理由**: 出典データは**書き換えの頻度も担当も違う**（問題集を読む
作業と、作問する作業は別）。混ぜると衝突する。ビルド時ではなく**検査時に突き合わせる**
（tests.js が「対応表のコードが実在するか」を見る）。

`questions.json` 側の `source` は、対応表から**生成して流し込む**（手書きしない）。

## 5. 進め方（第1段 → 第3段）

### 第1段: 有機だけ・Lv の検証（まずここ）

1. セミナーの**有機分野の目次と問題番号**を機械可読にする（`seminar_map.jsonl` の骨）。
   問題文は読まず、**章立てとレベル区分と問題番号**だけを拾う
2. qa の有機10単元283項目と対応づける。**1問→複数コード**でよい
3. **現在の difficulty と突き合わせて食い違いを一覧にする**
   → これが第1段の成果物。「感覚で付けた Lv がどれだけずれていたか」が出る
4. 食い違いをレビューして difficulty を更新（**機械的に上書きしない**。
   TAXONOMY §2 の「概念が易しくても頻度が低ければ Lv2 に上げない」等の判断が要る）

### 第2段: 頻度（`freq`）

5. `_解析/index.json` は分野レベルなので、**qa コード単位の頻度は出せない**。
   コード単位が要るなら `_解析/db/problems.jsonl`（現在10問）を育てる必要がある
6. **当面の代替**: 分野レベルの頻度を qa の `group` に割り当てて粗い優先度を出す。
   「志望校で頻出かつ未定着」の精度は落ちるが、**無いよりは効く**
7. 大学別（`freq.univ`）は問題DB が育ってから

### 第3段: アプリへの反映

8. 習得マップで「頻出かつ未定着」を優先表示（TAXONOMY §2.7・プレミアム／B2school 向け）
9. 出題順の優先度に頻度を混ぜるかは**要判断**（現状は誤答＞未着手＞定着度の順）
