# 申し送り: 一問一答セッションを問題データベースセッションに合流させる（2026-08-13）

**この文書は引き継ぎだけで、`qa/` のコードもデータも変更していない。** 実際に手を入れるのは受け取った側の仕事。
書いたのは assembler の統合レーン（`/assembler/` 担当）で、`qa/` の当事者ではない。
**中の判断（どの根拠をどう使うか）はすべて既存の設計書が正**で、ここはその**在りかと順番**だけを示す。

- 進捗と設計の正は `qa/DESIGN_difficulty_frequency.md`。とくに **§7-6（段階）** と **§8-4（第2便の中身）**
- 知識項目の分類と `freq` の予約形は `qa/TAXONOMY.md` §2.7
- 教科書の単純化に足をすくわれないための目録は `qa/KNOWLEDGE_CAVEATS.md`

---

## 1. なぜ合流させるのか（向きに意味がある）

ユーザー判断（2026-08-13）: **一問一答セッションと問題データベースセッションを1本にする。**
**向きは「データベースが一問一答を吸収する」**で、一問一答を畳むのではない。

**「一問一答は役目を終えた」という見立ては、状況としては正しく、結論としては誤り。**
終わったように見えるのは、**止まっているから**で、理由は3つの事実にある:

1. **問題データベースは別物ではなく、`qa/` の中にある。**
   `qa/data/`・`qa/tools/`・`qa/gemini-pack-*.md` はすべてデータベース側の資産。
   直近25コミットの `qa/` はほぼ全部がデータベースの作業だった
2. **アプリはすでにデータベースの出口になっている。**
   `qa/app.js` の `usageHtml()`（§出題実績の帯・2026-08-11）が `data/exam_usage.jsonl` を読んでいる。
   **集めた根拠が人の目に触れる面はここしかない**（`_解析/` は解析レーンの作業場で、公開面を持たない）
3. **アプリ側の仕事は終わっていない。** §7-6 の**第3段が丸ごと未着手**で、
   そこは「データが届く」ではなく「**アプリが映す**」仕事。
   TAXONOMY §2.7 の「**頻出かつ未定着**」は第3段でしか出せない

つまり第2段→第3段は「**根拠が届く → アプリが映す**」という**1本のパイプライン**で、
途中に切れ目がない。2セッションに割ると納品のたびに引き継ぎが要る ——
そして下の §2 のとおり、**実際にそこで7ファイル分が宙に浮いた**。

## 2. ⚠ 最初にやること: 宙に浮いている第2便を着地させる

**この文書を書いた時点で、`qa/data/` に未コミットの納品が乗っている。**
どちらのセッションの担当でもない中間物になっていた。

| ファイル | 中身 | 差分 |
|---|---|---|
| `data/seminar_process_ch20/21/23/24/25/26/27.jsonl` | 第2便A（セミナーのプロセス・7章） | 新規7件 |
| `data/exam_answer_type.jsonl` | 第2便B（①解答になるか・11〜50位） | **+1244行** / −109 |

**受け入れ検査は通っている**（統合レーンが `node qa/tools/verify_new_evidence.js` を実行・**ハードエラー0件**）:

```
A. セミナーのプロセス … 8章 / 39項目 / 参照コード 86種
   codes が空の行: 0
   プロセスに出たコードの現行 Lv: {"1":20, "2":60, "3":5, "4":1}
   → プロセスに出るのに Lv3以上（下げ候補・強い信号）が 6件
     org.alcohol.methanol-prep / org.alcohol.ethanol-prep / org.aro.nitrobenzene-props
     org.bio.cellulose-fiber(Lv4) / org.poly.polyamide-silk / org.poly.urea-melamine-alkyd
   → Lv1 の 37件のうち、プロセスに出なかったのは 17件（教科書側の情報で決める）

B. 入試の「解答になる」判定 … 1579行
   値の分布: {"false":1407, "null":134, "true":38}
   既存の exam_usage.jsonl と結合できた: 1579 / 1579（100%）
   判定が付いたコード: 50 / 274種

C. 教科書での扱い … 316項目 / {"本文":303, "発展欄":10, "見あたらない":3}
   一致が弱い（判定を信用しない）: 131件
```

**§8-4 が発注した第2便は、これで A も B も届き切っている**（A は 22章が既コミット＋この7章で全8章、
B は「11位から50位まで」の予定どおり 50/274）。**次の発注は無い** ——
§8-4 は「51位以降は50位までの傾向を見てから決める」としているので、
**決めるのは第3段を一度通してから**。

⚠ **この未コミットは、すでに公開ゲートを塞いでいる。** `node tools/verify-release.js` が
**「qa: 1件の変更があるのに ?v= が v81 のままです」で落ちる** ——
規則5は作業ツリーを見るので、`data/exam_answer_type.jsonl`（`app.js` が読む＝配信物）が
変わったまま版が据え置きなのを検出する。
**つまり、いま `qa` を触る誰もがコミット前の門番を通せない**（`.md` と `tools/` は除外されるので、
設計書や依頼パックの更新だけなら落ちない ＝ 今日まで気づかれずに済んでいた）。
**着地させれば直る**（データを入れて `qa` の版を上げる、が1組）。

⚠ **統合レーンはこれをコミットしていない。** 並行セッションの作業を自分の件名で取り込むのは、
`DEVELOPMENT.md` に記録した事故①（`add` と `commit` を分けると相手に吸われる）と**同じ害**を
逆向きにやることになるため。**合流後の最初のコミットとして、当事者が出すのが正しい。**

⚠ 数字を1つ読み違えないこと: **B の `true` は 38 しかない**（1579行中）。
これは「①解答になる」が稀だという意味であって、データが薄いという意味ではない。
§7-3 の「①解答になる回数が多い＝暗記必須度が高い（強い）」は、**そもそも母数が小さい強い信号**として設計されている。

## 4. 第3段の着手点（合流後の最初の設計判断）

形は §7-4 で決まっている。`questions.json` の各項目に `evidence` を持たせ、
**根拠の内訳を残したまま** `difficulty` と `priority` を導く:

```json
{
  "code": "org.ali.unsaturation",
  "difficulty": 2,
  "priority": "high",
  "evidence": {
    "textbook": "本文",
    "seminar": "基本",
    "exam": { "asAnswer": 12, "asTool": 45 }
  }
}
```

**着手の順に、決まっていることと決まっていないこと:**

1. **`evidence` を組み立てる**（決まっている）。4つの出典はすべて `data/` に揃った。
   `tools/apply_seminar_levels.js` が第1段でやったのと同じ形の変換で足りる
2. **`priority` の閾値を決める**（**未決・ここが判断**）。§7-3 は
   **「閾値は先に決めない。データが揃ってから分布を見て決める」**と明記している ——
   これは §3-5 の轍（初期案の対応表を先に作って外した）を踏まえた指示なので、**先に表を書かないこと**
3. **表示に載せる**（未着手）。TAXONOMY §2.7 の「頻出かつ未定着」＝ 習得マップの習得度 × `priority`
4. **出題順に混ぜるかは要判断**（§5 の項目9）。現状は「誤答 ＞ 未着手 ＞ 定着度」の順で、
   **頻度を混ぜるとは決まっていない**

**言ってはいけないことが1つある**（§7-3）。**「出ていない＝優先度が低い」とは言わない。**
母集団は2021年入試の有機140大問の1年分で、316項目のうち **73項目は入試DBだけ・34項目は
セミナーにも入試DBにも出ない**。`priority: "unknown"` を潰さずに残すこと。

## 5. 合流したセッションが引き継ぐ約束（`qa/` 固有のもの）

- **`qa/` を触ったら `qa/test.html` を必ず開く。** データの事故（重複コード・正解添字のずれ・
  Markdown 記法の混入・下付き文字のもれ）と**版の同期**を検査している
- ⚠ **`qa/app.js` 内の `questions.json?v=NN` は `tools/verify-release.js` の死角**（.html しか見ない）。
  ここを塞ぐテストが `qa/tests.js` に入っているので、**版を上げたら test.html を開くまでが1組**
- データ部分だけなら node でも走る:
  `node -e "const{runDataTests}=require('./qa/tests.js'); ..."`
- **隣のアプリのデータは必ずキャッシュを外して読む**（`qa/test.html` 冒頭の注記）。
  `?v=` は自分のアプリの版に合わせる仕組みなので、**相手のファイルには効かない**
- コミットは**パス指定**（`git commit <paths> -m …`）。**`commit -a` は禁止**。
  作業ツリーは assembler / 動画生成レーンと共有している

## 6. 統合レーン（assembler）との境界

- **`qa/` には統合レーンは手を出さない。** この文書と、§2 の受け入れ検査を走らせたことだけが接触点
- 往復リンク（`qa` ⇄ `assembler` の「来た道」の帯）は **assembler 側の `tests.js` の QB1〜4** が見張る。
  `qa/data/assembler_links.jsonl` を変えたら、assembler の test.html も通ること
- assembler 側の版・テスト・公開は統合レーンが持つ。**`qa` の版は `qa` が持つ**
