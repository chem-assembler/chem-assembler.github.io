# B群: 酸化還元モードの設計（2026-07-23）

ユーザー方針: **半反応式だけをアニメーション化し、それらを任意の整数倍して足し合わせる**。
半反応式が「部品」、倍率合わせが「組み立て」。e⁻ の数合わせが本モードの核心。

## 学習ループ（イオン反応モードと同型）

1. **半反応式が部品として提示される** — [酸化] Zn → Zn²⁺＋2e⁻ ／ [還元] Ag⁺＋e⁻ → Ag
2. **倍率 ×a・×b を操作** — ビーカー内の配置（板の上の原子 a 個・溶液中のイオン b 単位）が即座に連動
3. **「▶ 反応を見る」** — 酸化: 板の原子が e⁻ を出してイオンになり溶け出す →
   還元: 溶液のイオンが板へ泳ぎ、板の e⁻ を受け取って原子になり析出（金属樹）／H₂ の泡になる
4. **失敗の表現**（発見学習）
   - e⁻ が余る → 板の上で赤く点滅「e⁻ が n 個余った。受け取る相手が足りない」
   - e⁻ が不足 → イオンが板の前で待ちぼうけ「e⁻ が足りない」
5. **ぴったり** → 足し合わせ表示: `Zn ＋ 2Ag⁺ ＋ ~~2e⁻~~ → Zn²⁺ ＋ 2Ag ＋ ~~2e⁻~~`
   と e⁻ を打ち消し線で消し、まとまったイオン反応式を提示。倍率＝係数の実感
6. クリア条件 = アニメがぴったり完了 ＋ 倍率が最簡整数比

## モデル（model.js に追加・純ロジック）

- 化学種: Zn / Zn²⁺ / Cu / Cu²⁺ / Ag / H₂ / **e⁻**（atoms 空・charge −1 の特別種）
- `HALF_REACTIONS`: { disp, left: [{sp,n}], right: [{sp,n}], kind: oxidation|reduction }
  - 半反応式自体が原子・電荷保存を満たすことをテストで機械検証
- `REDOX_STAGES`: { ox, red, answer: [a,b] }
- `checkRedoxMultipliers(stage, a, b)`: e⁻ 授受が等しい ＆ gcd(a,b)=1
- `combineHalves(stage, a, b)`: 両辺を倍率つきで合算し、両辺に現れる種（e⁻）を打ち消して
  イオン反応式を返す。結果が compareSides で釣り合うことをテストで検証

## 画面（redox.html + redox.js。model.js と style.css を共用）

- index.html とヘッダーで相互リンク（モード切り替え）
- ステージ: r1 Zn×Cu²⁺（1:1）／ r2 Cu×Ag⁺（1:2 倍率合わせの本番）／ r3 Zn×2H⁺（H₂ 泡）
- ビーカー左に金属板。e⁻ は黄色の小粒として板の上に「たまる」→ 受け手へ飛ぶ
- 検証はイオン反応モードと同じ思想: 個数（e⁻ プール・待ちイオン・析出数）のみで判定、
  座標は見た目専用。`window.RedoxEq.advance(ms)` フックで UI テスト駆動

## 将来（このエンジンの延長）

- イオン化傾向シリーズ（どちらが溶けてどちらが析出するかの予想モード）
- B3 電池: 2枚の板と導線で e⁻ を回す（半反応式部品はそのまま流用）
- 半反応式そのものを組み立てる練習（e⁻ の数を自分で決める）

## 溶液中の酸化還元（redox-solution・2026-07-24 追加設計）

金属樹（`redox-metal`）は「板＋溶液イオン」前提。KMnO₄・K₂Cr₂O₇ などは**酸化剤も還元剤も溶液中**で、
H⁺ が反応に関与し、**色変化**が最大の見どころ（酸化還元滴定の終点＝色が変わる/残る）。
[DESIGN_reaction_library.md](DESIGN_reaction_library.md) の animationType レジストリで `redox-solution` として扱う。
**モデルは既存の枠（半反応式×倍率→e⁻ 打ち消し→イオン反応式）をそのまま流用**し、拡張は (1) 半反応式データ
(2) 酸化数表 (3) 色データ、と**アニメが新規**の3点に閉じる。

### モデル拡張（model.js・純ロジック）

**HALF_REACTIONS 追加**（酸化剤側に H⁺ と H₂O が入る。原子・電荷保存＋e⁻ を含むことを既存テストで検証）:

| id | 半反応式 | kind | e⁻ |
|---|---|---|---|
| `MnO4_red` | MnO₄⁻ ＋ 8H⁺ ＋ 5e⁻ → Mn²⁺ ＋ 4H₂O | reduction | 5 |
| `Cr2O7_red` | Cr₂O₇²⁻ ＋ 14H⁺ ＋ 6e⁻ → 2Cr³⁺ ＋ 7H₂O | reduction | 6 |
| `Fe2_ox` | Fe²⁺ → Fe³⁺ ＋ e⁻ | oxidation | 1 |
| `H2O2_red` | H₂O₂ ＋ 2H⁺ ＋ 2e⁻ → 2H₂O | reduction | 2 |
| `H2O2_ox` | H₂O₂ → O₂ ＋ 2H⁺ ＋ 2e⁻ | oxidation | 2 |
| `oxalate_ox` | (COO)₂²⁻ → 2CO₂ ＋ 2e⁻ | oxidation | 2 |
| `I_ox` | 2I⁻ → I₂ ＋ 2e⁻ | oxidation | 2 |

代表 REDOX_STAGES（溶液中）: MnO₄⁻×Fe²⁺（1:5）、Cr₂O₇²⁻×Fe²⁺（1:6）、MnO₄⁻×(COO)₂²⁻（2:5）。
`checkRedoxMultipliers`/`combineHalves` は無改修で流用（e⁻ 数を合わせ最簡比、両辺共通種を打ち消し）。
※ combineHalves は現状 e⁻ しか打ち消さないが、溶液中では H⁺・H₂O は打ち消し対象にならない（片辺のみ）ため問題なし。
両辺に同種が残るケース（例外的に H₂O が両辺）が出たら打ち消し一般化を検討。

**OXIDATION 拡張**（「原子の酸化数合計＝種の電荷」を既存テストで機械検証）:
`MnO4-`={Mn:+7, O:−2}、`Mn^2+`={Mn:+2}、`Cr2O7^2-`={Cr:+6, O:−2}、`Cr^3+`={Cr:+3}、
`Fe^3+`={Fe:+3}、`H2O`={H:+1, O:−2}、`O2`={O:0}、`H2O2`={H:+1, O:−1}（**過酸化物の O=−1 は例外**）、
`CO2`={C:+4, O:−2}、`(COO)2^2-`={C:+3, O:−2}、`I-`={I:−1}、`I2`={I:0}。
- 多原子イオンの酸化数は O=−2・H=+1 を基準に逆算するのが通例だが、本アプリは**値を直接 OXIDATION に持つ**
  （逆算ロジックは持たない）。過酸化物のような例外もデータで表現でき、検証もデータ駆動で回る。
- `oxChangeOfHalf` は「変化する元素がちょうど1つ」を仮定。MnO₄⁻→Mn²⁺（Mn のみ変化）等は満たす。
  H₂O₂ の不均化（O が +?）など1元素の増減が非自明な反応は当面ステージにしない（要注意メモ）。

### 色データ（新規・見た目専用だが機械検証する）

種→色の表 `SPECIES_COLOR`（有色種のみ。無色は既定の淡色）:
`MnO4-`=赤紫、`Mn^2+`=ほぼ無色、`Cr2O7^2-`=橙、`Cr^3+`=緑、`Fe^2+`=淡緑、`Fe^3+`=黄褐、`I2`=褐。
- **粒の色**＝その種の色（房/円の塗り）。
- **溶液全体の色**＝現存する有色種の量で決まる混合色。滴定では「酸化剤（紫）が残るか」で終点を判定・演出。
- 検証: 半反応式・反応に登場する有色種すべてに色定義があること（データ駆動テスト）。

### アニメーション（redox.js を拡張 or 新 renderer）

`redox-metal`（板あり）と分岐。`redox-solution` は**板なし・両者とも溶液中の浮遊粒**:

1. 倍率 ×a・×b に応じて酸化剤 a 単位・還元剤 b 単位＋H⁺ を配置
2. 「▶ 反応を見る」で、還元剤が e⁻ を放ち（黄粒）、酸化剤が受け取る。酸化剤は H⁺ を取り込んで
   Mn²⁺＋H₂O 等に変化（房の作り替え）。**変化の瞬間に粒の色が遷移**（紫→無色 など）
3. **溶液全体の背景色**も反応進行で遷移。ぴったりで無色化（=終点）
4. 失敗表現は既存流用: e⁻ 余り＝赤点滅、不足＝待ちぼうけ。過剰の酸化剤＝**紫が残る**（滴定の実感）
5. ぴったり＋最簡比でクリア。足し合わせ→イオン反応式（H⁺・H₂O 込み）を表示

判定は既存思想どおり**個数のみ**（e⁻ プール・変化した粒数・残留有色種数）。色・座標は見た目専用。
`window.RedoxEq` フックに溶液色/残留有色種を足して UI テストで駆動する。

### reactions.json との接続

- 溶液中反応は `animationType:"redox-solution"`、`classes.redox:"溶液中の酸化剤還元剤"`。
- **実装済み**（v29〜）。索引の「▶ 酸化還元モードで見る」から `redox.html?rxn=<REDOX_STAGE の id>` へ飛ぶ
  （redox.js にも ?rxn ディープリンク受けを追加。app.js と同型）。
- 遊べるかどうかは**手で書かない**（v164 で `playable` を廃止）。`animationType` の
  レジストリが行き先の画面と参照フィールド（`redoxStage`）を宣言し、そのステージが
  `REDOX_STAGES` に実在すれば遊べる ＝ **ステージを足せば索引にも自動で「▶遊ぶ」が出る**。
  詳細は [DESIGN_reaction_library.md](DESIGN_reaction_library.md) の「アニメーションタイプ・レジストリ」。

## はじめに入れたものから化学反応式を組み立てる（bottles・2026-08-18・v180）

### なぜ要るのか（ユーザーの申し立て）

イオン反応式までは書けるのに、そこから化学反応式に進めない。つまずきは2つあり、
どちらも**規則を覚えていない**のではなく、**式の左辺が何なのかを取り違えている**ことから来る。

1. **なぜ硫酸イオンを加えるのか分かっていない** — 「両辺に SO₄²⁻ を足す」という操作だけを覚えると、
   SO₄²⁻ が天から降ってくることになる。実際は **H₂SO₄ を入れたから H⁺ と一緒に来た**だけで、
   足しているのではない。
2. **イオン反応式の左辺にあるイオンどうしを組んでしまう** — KMnO₄ ＋ KI の左辺には H⁺ と I⁻ が
   並ぶので、`HI` を作ってしまう。だが H⁺ を連れてきたのは H₂SO₄、I⁻ を連れてきたのは KI で、
   **この2つは互いを連れてきていない**。

既存の④⑤（`molecularEq` の筆算＝「両辺に傍観イオンを何個足すか」）は、1 を注記1行で済ませ、
2 には触れていない。**「両辺に足す」という言い方そのものが 1 の誤解と同じ形**をしている。

### 決めた形（ユーザー選択・2026-08-18）

ビーカーに実際に入れた**物質**から出発する。

```
  ビーカーに入れたもの   【KMnO₄】【FeSO₄】【H₂SO₄】
        ↓ 溶ける
  水の中のイオン         K⁺ MnO₄⁻ ／ Fe²⁺ SO₄²⁻ ／ H⁺ SO₄²⁻
        ↓ 反応（★ここまでは既存の①〜③）
  イオン反応式           5Fe²⁺ ＋ MnO₄⁻ ＋ 8H⁺ → 5Fe³⁺ ＋ Mn²⁺ ＋ 4H₂O
        ↓ 水を蒸発
  残ったイオンが対で塩に  2KMnO₄ ＋ 10FeSO₄ ＋ 8H₂SO₄ → 5Fe₂(SO₄)₃ ＋ 2MnSO₄ ＋ K₂SO₄ ＋ 8H₂O
```

**左辺は組み立てない。はじめに入れたものがそのまま左辺になる。** ここが要で、だから `HI` は作りようがない
（HI を入れていない）。学習者がやるのは「左辺の各イオンは**どのもとの物質が連れてきたか**」を言うことだけ。

### データの形（model.js）

ステージが持つのは**入れたものの並び1本**だけ。ほかは全部そこから導く（対応表を手で書かない・DEVELOPMENT.md 設計原則）。

```js
{ id: "rs1", ox: "Fe2_ox", red: "MnO4_red", answer: [5, 1], mode: "solution",
  bottles: ["KMnO4", "FeSO4", "H2SO4"] }
```

導出に使う既存の資産:

| 使うもの | 何に使うか |
|---|---|
| `DISSOCIATION` | 入れた物質が溶けて出すイオン。**載っていないもの（Zn・Cu・C₂H₅OH）はそれ自身1個**として扱う（＝金属板・分子もこの枠に収まる） |
| `combineHalves` | イオン反応式。倍率 a・b は既存の③で決まったものをそのまま使う |
| `SPECIES[].charge` | 塩の組成（陽イオン何個 ＋ 陰イオン何個）。**個数は電荷から導く** |

新しく持つ表は1つだけ:

```js
const SALT_FORMULA = { "Fe^3+|SO4^2-": "Fe2(SO4)3", "K+|SO4^2-": "K2SO4", … };
```

**個数は書かない**。`saltUnit(cation, anion)` が電荷の最小公倍数から `{ cn, an }` を出し
（Fe³⁺ と SO₄²⁻ なら lcm(3,2)=6 → 2 と 3）、`to` の組成式の原子数と突き合わせて検算する
（回帰テスト）。ここを手書きすると `Fe(SO₄)` のような釣り合わない塩が黙って通る。

### 導出の手順（`bottlePlan(stage, a, b, scale)`・純ロジック）

1. `ionic = combineHalves(stage, a, b)` を `scale` 倍する。
2. **左辺のイオンに物質を割り当てる**。物質 B が出すイオンのうち、イオン反応式の左辺に現れるものが
   B の担当。「左辺の各イオンをちょうど1つの物質が担当する」ことをデータ検査で要求する。
3. **本数を割り算で出す** — 担当イオンが n 個要り、その物質1つが p 個出すなら `⌈n/p⌉` 本。
   1本が複数の担当を持つときは各担当の最大（HNO₃ は H⁺ 8個 と NO₃⁻ 2個 を担当するので 8本。
   余った NO₃⁻ 6個は傍観へ回る ＝ **硝酸の二役がこの計算に自然に入る**）。
4. **蒸発後のプールを作る** — イオン反応式の右辺 ＋ 入れた物質すべての傍観イオン。
   電荷 0 のもの（H₂O・NO・CO₂・I₂・析出した Cu・H₂・アルデヒド）は**そのまま右辺に残る**。
5. **対にして塩に戻す** — 陽イオンごとに `saltOf(陽, 陰)` を引き、`cn` 個ずつ束ねる。
   陰イオンは**プールにちょうど1種**であることを要求する（2種あるとどちらと組むかがデータの決めごとになる）。
6. 割り切れなければ `ok:false`。`minBottleScale` が 1 から順に試して、最初に成立する倍率を返す。

**倍率が要ることが、そのまま山場になる。** rs1 は Fe³⁺ が5個できるが Fe₂(SO₄)₃ は2個ずつしか
使えないので1個あまる → **全体を2倍**して 10Fe³⁺ にすると 5 個ぴったり組める。
rs2 は Fe³⁺ が6個なので**倍にしなくてよい**。この対比を2ステージ並べて見せる。

### 画面（redox.js・`#stepBottles`）

`stage.bottles` があり、かつ**既存の筆算（`molecularEq`）を持たない**ステージにだけ出る新しい段。
③（イオン反応式）が最簡整数比まで片づいたら現れる。

- **④ ビーカーに入れたもの — どのもとの物質が連れてきた？**
  左辺のイオンごとに `<select>` を1つ。選択肢は**導出**する:
  - 入れたものの棚の全部（正しい1つと、そのイオンを出さない残り）
  - **左辺にいる反対符号のイオン**（＝「◯◯ と組む」。これが罠で、KMnO₄×KI なら `H⁺ と I⁻`）
  正しく答えると、その物質が溶けてイオンに分かれる姿と**一緒に来た傍観イオン**が出る。
  全部そろうと⑤が現れる。
- **⑤ 水を蒸発させる — 残ったイオンが対で塩に戻る**
  ~~「全体を ×N」のステッパー1つ。~~ → **v182 で作り直した。下の「実機レビュー（2026-08-18）」を見ること。**

### 失敗の見せ方（**黙って弾かない**）

| 選び方 | 出る文言（`explainBottleOwner` が1か所で持つ） |
|---|---|
| 正しい物質 | 「そのとおり。KI は水にとけて K⁺ と I⁻ に分かれる。一緒に来た K⁺ は反応しないが、ビーカーの中にはいる。」 |
| そのイオンを出さない物質 | 「H₂SO₄ が水にとけて出すのは H⁺ と SO₄²⁻。I⁻ は出さない。」 |
| **左辺の別のイオンと組む** | 「**H⁺ と I⁻ は互いを連れてきていません。** H⁺ を連れてきたのは H₂SO₄、I⁻ を連れてきたのは KI。イオン反応式の左辺は、水の中でばらけたあとの姿。ここに並ぶイオンどうしを組み直しても、はじめに入れた物質にはならない。」 |
| 倍率が足りない | 「Fe³⁺ が 5個。Fe₂(SO₄)₃ は Fe³⁺ を 2個ずつ使うので 1個あまる。全体を倍にしてみよう。」 |
| 倍率が多い | 「係数がすべて 2 で割り切れる。×1 に戻そう。」 |

### 収録の範囲と、入れなかったもの

| ステージ | 入れるもの | 扱い |
|---|---|---|
| rs1 KMnO₄×Fe²⁺ | KMnO₄ / FeSO₄ / H₂SO₄ | **画面に出す**（×2 が要る側） |
| rs2 K₂Cr₂O₇×Fe²⁺ | K₂Cr₂O₇ / FeSO₄ / H₂SO₄ | **画面に出す**（×1 で済む側） |
| r1〜r4 金属×イオン | Zn / CuSO₄ など | **画面に出す**。電離表に無い金属は「それ自身1個」で同じ仕組みに乗る。いちばん短い例 |
| ro1〜ro3・rn1・rn2 | 既存 | **データだけ足し、画面は変えない**（下記） |
| **rs3 KMnO₄×シュウ酸** | — | **入れない**（下記） |
| ri1・ri2 ヨードホルム | — | **入れない**（下記） |

**rs3 を入れない理由（2つ・どちらも独立に致命的）**
1. シュウ酸は**弱酸**で、高校の模範解答ではイオン反応式でも H₂C₂O₄ 分子のまま書くのが通例
   （model.js の rs3 に既にある注記・J-1）。④⑤に載せると「H₂C₂O₄ を入れたのに完全には電離しない」
   という**この段とは別の話**が混ざる。現行の提示形は C₂O₄²⁻ なので、入れた物質（H₂C₂O₄）と
   イオン反応式（C₂O₄²⁻）で書き方が食い違うことになる。
2. 仕組みの上でも乗らない。H₂C₂O₄ を完全電離とみなすと **H⁺ が H₂C₂O₄ と H₂SO₄ の2本から出る**ので、
   手順2の「左辺の各イオンをちょうど1つの物質が担当する」が壊れる（HNO₃ の二役は
   1本が複数のイオンを担当する形で吸収できるが、こちらは**1つのイオンを複数の物質が担当する**形で別もの）。
   これを一般化すると連立方程式になり、「割り算で本数が出る」というこの段の見え方が消える。
   → **教科書の式**（2KMnO₄ ＋ 5H₂C₂O₄ ＋ 3H₂SO₄ → 2MnSO₄ ＋ K₂SO₄ ＋ 10CO₂ ＋ 8H₂O）**は正しい**
   ので、扱えないのはこの図法の限界。将来やるなら「弱酸は分子のまま書く」を先に決着させてから。

**ri1・ri2 を入れない理由**: 左辺に `CH₃⁺`（切り出した断片）が並ぶ。これはビーカーに入れるものではないし、
教科書の全体式は既に `IODOFORM_CLEAVAGE[].overall` で出している（NaOH を含む別の書き方）。

**既存の `molecularEq` 5本をどうしたか（＝2つの作り方が並ぶ理由）**

`bottles` は**5本すべてに足す**が、**画面は1ピクセルも変えない**。値打ちは
「**同じ導出が、手で書かれた5本の模範係数をそのまま再現する**」ことの機械検査にある
（M6-A で `composeStage` を入れたときと同じ形）。これで、rs1・rs2 のために新しく作った導出が
**すでに検算済みの5本**に裏を取られる。

画面を移さない理由は、④⑤の筆算が**別の問いに答えている**から:
- **筆算**（`molecularEq`）… 「イオン反応式の両辺に傍観イオンを何個足すと分子の姿に戻るか」。
  硝酸のように**酸と酸化剤を兼ねる**項の係数が電子だけでは決まらない反応（rn1・rn2）や、
  K⁺ の数が酸化剤の係数から決まっている反応（ro1〜ro3）は、この筆算がそのまま山場になる。
- **入れた物質**（`bottles`）… 「実験で入れたものから、どうやって式の左辺ができるか」。
  申し立ての2つのつまずきはこちら側にある。

どちらかに寄せるかは、**両方を実際に触ってから**決める（いま決めると、片方を作る前に片方を捨てることになる）。
寄せるとしたら向きは「筆算 → 入れた物質」で、そのとき `molecularEq` は
「④⑤の言い回しを持つデータ」に縮む（係数は `bottlePlan` が出せる）。

## 実機レビュー（2026-08-18・v182）— ⑤を数入力にし、倍率を例外へ落とす

上の設計で作った v180/v181 をユーザーが実際に触って出した指摘（台帳は
[ORDER_review_2026-08-18.md](ORDER_review_2026-08-18.md) の B・D）。原文:

> どのイオンを何個加えるか、というところを入力することに意味があります（実際に反応式を書くときに必要な作業）

> イオン反応式全体を2倍するのは、レアケース、右辺で係数に1/2がでてきたときに必要な措置です
> 他の場合は考慮する必要がありません

**残したもの / 変えたもの**

| | v181 | v182 | なぜ |
|---|---|---|---|
| ④ 誰が連れてきた？ | 選択肢（罠つき） | **そのまま残す** | 「左辺のイオンどうしを組む」つまずきに効くのはここだけ。指摘は④を否定していない（否定されたのは**金属樹に**この段を出すこと ＝【A】で別途対応） |
| ⑤ の入力 | 「全体を ×N」のステッパー1つ | **物質ごとの個数の数入力**に置き換え | 下の B |
| ⑤ の本数の割り算 | 画面が**答えを表示**していた | **学習者が入力し、外したら差を言う** | 同上 |
| 全体の倍率 | 常設のステッパー | **半端が出たときだけ現れる案内＋釦** | 下の D |
| 導出（`bottlePlan`）| — | **1行も変えない** | v180 の機械検査（既存 `molecularEq` 5本の模範係数を再現する）を安全網として温存するため |

### B. ⑤は「何個加えるか」の数入力にする — ただし「両辺に足す」とは言わない

**統合レーンの見立て「④と⑤の両方が要る」は正しい。** ④が答えるのは**どこから来たか**、
⑤が答えるのは**何個か**で、問いが別。前レーンが⑤に反対したのは
「**両辺に傍観イオンを足す**」という**言い方**に対してであって、
**数を数えさせること自体には反対していない**。ここを分ければ両立する。

**そこで、同じ数を別の問いで取りに行く。**

```
  筆算の言い方   「両辺に SO₄²⁻ を 18個ずつ足す」   ← 18 が天から降ってくる
  もとの物質の言い方     「H₂SO₄ を 8本、FeSO₄ を 10本入れた。SO₄²⁻ は 8＋10＝18個ついて来た」
```

**答えは同じ 18。だが後者には「足す」という操作が一度も出てこない。**
④で「SO₄²⁻ は H₂SO₄ が連れてきた」と言ったばかりなのだから、⑤で
「では何個ずつ足しますか」と聞いたら、④で言ったことを⑤が取り消すことになる。

**入力させるのは物質ごとの個数**（＝ 化学反応式の左辺の係数そのもの）。
本数を決めれば、ついて来るイオンの数は掛け算で決まる ＝
「**どのイオンを何個加えるか**」の答えがそのまま出る。

```
  KMnO₄ を [  ] 本      MnO₄⁻ が 1個 要る ／ KMnO₄ 1本が出すのは K⁺ ＋ MnO₄⁻
  FeSO₄ を [  ] 本      Fe²⁺ が 5個 要る ／ FeSO₄ 1本が出すのは Fe²⁺ ＋ SO₄²⁻
  H₂SO₄ を [  ] 本      H⁺ が 8個 要る ／ H₂SO₄ 1本が出すのは 2 H⁺ ＋ SO₄²⁻
                        ↑ ここの ÷2 が、この段でいちばん外れるところ
```

そろったら、ついて来た傍観イオンの合計を1行で出し、**そこで初めて筆算の言い方と橋を架ける**:
「SO₄²⁻ はぜんぶで 18個。筆算で『両辺に SO₄²⁻ を 18個ずつ足す』と書くのは、この18個のこと。」

**採らなかった案**

- **`molecularEq` の `spectator` ステッパー（「何個足すか」1つ）をそのまま rs1 に移植する** —— 統合レーンが
  「その形を持ってくるのが素直」と書いた案。数としては等価だが、④の直後に置くと上記のとおり
  ④を打ち消す。**筆算そのものは ro1〜ro3・rn1・rn2 に現に残っている**ので、
  この形が消えるわけではない（2つの作り方が並ぶ理由は上節のまま）
- **右辺（塩の個数）も入力させる** —— 「実際に反応式を書く作業」には右辺も含まれるが、
  右辺の対の作り方は④の「水を蒸発させる」の絵がそのまま答えを見せている。
  ここを入力にすると**絵を読んで写すだけ**の欄が4つ増える。左辺の割り算だけが、
  絵を見ても答えが出ない ＝ 入力させる値打ちがある
- **傍観イオンの総数（18）を直接入力させる** —— 物質の個数を経由せずに 18 を出す道が無い
  （18 は 8＋10 であって、単独では数えられない）。先に本数を聞くのが順番として正しい

### D. 全体の倍率は「例外」なので、常設の工程から外す

v181 は「全体を ×N」のステッパーを⑤に**常設**していた。しかも `rs1` がちょうど
×2 の要る回なので、**例外が既定の顔をしていた**。ユーザーの言うとおりこれは
「右辺で係数に 1/2 が出たときにだけ要る措置」で、ふだんは考えなくてよい。

**変えたのは言い方ではなく出し方**（v181 の文言はすでに「Fe³⁺ が5個。Fe₂(SO₄)₃ は
2個ずつ使うので1個あまる」と言っていた）。

```
  ふつう（rs2・r3）  本数を入れる → 塩に組む → 化学反応式。倍率の話は一度も出ない
  例外（rs1）        本数を入れる → 塩に組もうとすると Fe³⁺ が1個あまる
                     → ここで初めて案内が出る:
                       「Fe₂(SO₄)₃ が 2.5個 ＝ 係数に 1/2 が出てしまう。
                         こういうときだけ、式の全体を2倍して整数にそろえる」
                       [ 全体を ×2 にしてそろえる ]  ← 押すと本数も倍になる
```

- **半端が出ていないときは、倍率という言葉を画面に出さない**（`bottleScaleAdvice` が `null` を返す）
- 案内には **`2.5個` という半端そのもの**を出す。ユーザーの言う「1/2 が出てきたとき」を
  画面の言葉と一致させるため。v181 は「1個あまる」までしか言っていなかった
- **倍率を探させない。** ×N のステッパーを残すと「例外を常設する」に戻る。
  釦は1つで、行き先（×2）は `minBottleScale` が出す。この段の学びは
  「**半端が出たことに気づく**」ことであって、倍率の総当たりではない
- 押したら**入力済みの本数も同じ倍率で掛ける**（学習者が自分で出した値がそのまま2倍になって見える）。
  戻す釦（`×1 に戻す`）も同じ場所に置く

⚠ **`rs1` は実際に ×2 が要るので、この例外の道が本当に通ることを実測で確かめる**（回帰テストにも入れる）。

## G. 金属樹を除いて化学反応式まで（2026-08-18・v187）

ユーザーの指示:「**酸化還元は、金属樹、を除いて化学反応式までかけるように**」。
【A】で金属樹（r1・r2・r4）を外したあと、残っていたのは **rs3・ri1・ri2** の3件。

### rs3（KMnO₄ × シュウ酸）— 収録した。**1つのイオンを複数の物質が担当する**への一般化

v182 までの `bottlePlan` は「左辺の各イオンを**ちょうど1本**の物質が担当する」ことを要求していた。
rs3 は `H⁺ 16個` が **H₂C₂O₄ と H₂SO₄ の両方**から出るので落ちる
（硝酸の二役＝1本が複数のイオンを担当する、とは向きが逆で別ものの一般化）。

**「1本以上が担当する」に広げた。連立方程式にはしない** —— 「割り算で本数が出る」という
この段の見え方が消えるため。代わりに2段で解く:

```
  段1  出どころが1本しかないイオンを先に決める
        C₂O₄²⁻ 5個 → H₂C₂O₄ 5本 ／ MnO₄⁻ 2個 → KMnO₄ 2本
  段2  出どころが複数のイオンは、段1で決まった物質が連れてくるぶんを引いて、
        残りを「残った1本」が出す
        H⁺ 16個 −（H₂C₂O₄ 5本ぶんの 10個）＝ 6個 → H₂SO₄ 3本
```

残った物質が1つに決まらないときだけ `dataError`。**既存8ステージの係数は1つも動かない**
（rn1 の硝酸の二役は段1の `max` のまま）。導けた式は教科書どおりで、倍率 ×1 で済む:

```
  2KMnO₄ ＋ 5H₂C₂O₄ ＋ 3H₂SO₄ → 2MnSO₄ ＋ K₂SO₄ ＋ 10CO₂ ＋ 8H₂O
```

**④の見せ場のほうへ変えた（前レーンの見送り理由への回答）**

前レーンは「弱酸という別の話が混ざる」として rs3 を見送った。だが**ユーザーはそれを教えたい**
——「シュウ酸は弱酸なので硫酸を加える必要がある」。**混ぜるのではなく、そこを見せ場にした。**

判断: **どちらから来たかを人に選ばせるのではなく、「両方から」を明示する。**
片方を正解にすると、実際は両方から来ているのだから**嘘を教えることになる**。
そのうえで、**片方だけを選んだときの「何個足りないか」**をこのステージの山場に置く。

| 選び方 | 出る文言 |
|---|---|
| **H₂C₂O₄ と H₂SO₄ の両方**（正解） | 「H⁺ 16個 は1つの物質では足りません —— H₂C₂O₄ が 10個、H₂SO₄ が 6個。**H₂C₂O₄ は弱酸なので、これだけでは酸性が足りない。残りを強酸の H₂SO₄ で補います**」 |
| H₂C₂O₄ だけ | 「H⁺ を出しますが、**10個 だけ**。16個 要るので **6個 足りません**」 ← なぜ硫酸を加えるのかが数で出る |
| KMnO₄（出さない物質） | 従来どおり「H⁺ は出しません」 |
| 左辺のイオンと組む（罠） | 従来どおり。出どころが2本あることも正しく言う |

⑤の手がかりも分担を明示する（「16個 要り、**そのうち 6個 がこちらのぶん**」）。
⚠ `H2C2O4` は**既に `DISSOCIATION` にある**ので、共有の表には触れていない。

### ri1・ri2（ヨードホルム反応）— **見送る**。この図法が原理的に成り立たない

⚠ 「難しいから」ではなく、**この図法の前提そのものが偽になる**ため。

④⑤の段の前提は「**イオン反応式の左辺 ＝ ビーカーに入れたもの**」だが、ri1 の左辺はこうなる:

```
  イオン反応式  CH₃⁺ ＋ 2I₂ → CHI₃ ＋ 2H⁺ ＋ I⁻
  教科書の全体式 CH₃COCH₃ ＋ 3I₂ ＋ 4NaOH → CHI₃ ＋ CH₃COONa ＋ 3NaI ＋ 3H₂O
```

食い違いが**3つ**あり、どれも出どころの割り当てでは埋まらない:

1. **左辺の `CH₃⁺` は入れたものではない** —— 段0 で `CH₃COCH₃` を切って作った断片。
   「はじめに入れたものがそのまま左辺」が最初から成り立たない
2. **I₂ が 2個ではなく 3個** —— 差の1個は、この段が扱っていない**もう片方の断片**
   （`CH₃CO⁻ ＋ H₂O → CH₃COO⁻ ＋ 2H⁺ ＋ 2e⁻`）が使うぶん。
   全体式は**半反応式3本＋切断**の和で、1本のイオン反応式からは出てこない
3. **NaOH がイオン反応式に1つも現れない** —— 生じた H⁺ を中和して塩（CH₃COONa・NaI）にする役で、
   これは酸化還元ではなく酸塩基。④⑤の段は「蒸発させて対にする」しか持っていない

**やるとしたら④⑤ではなく別の段**（3本の半反応式を足し、そのあと NaOH で中和する組み立て）が要る。
それはこの図法の一般化ではなく新しい仕組みなので、押し込まない。

⚠ **なお ri1・ri2 では、教科書の全体式は既に画面に出ている**（段0 の下・`IODOFORM_CLEAVAGE[].overall`。
「メチル側の I₂ 2個 ＋ 残った断片のぶん ＝ I₂ 3個」という説明つき）。
＝ **式は見えているが、組み立てさせてはいない**という状態。ここを組み立てさせたいなら上の別段が要る。

| ro1〜ro3・rn1・rn2 | ✅ | 筆算（`molecularEq`） |

### 0. いちばん大きい決め ── 容器を指す語を置き換えるのではなく、問いごと消す

★ **容器を指す語（ガラス容器の呼び名・試薬）を、`ion-equation/` の日本語からまるごと外した。**
別の語に言い換えるのではない。**問いを「MnO₄⁻ はもともと何だった？」に変えると、

### 7. 実装して分かったこと ── 設計と違った点（2026-09-08 実装後に追記）

★ **設計の中心（「作り直す必要が無い。5ステージを既存の段に通すだけ」）はそのとおりだった。**
9ステージすべてで導出が立ち、模範係数5本を項ごとに再現した。ただし**そのままでは通らなかった**。

**(1) ⑤が硝酸の二役で正解を弾いていた（本当のバグ・実装して初めて出た）**

`explainBottleCount` が担当イオンを **等号**で見ていた:

```js
const bad = row.covers.find((c) => c.per * n !== c.need);   // 旧
```

HNO₃ 8個 は NO₃⁻ を 8個 出すが、**反応するのは 2個 だけ**（残り6個は連れてきただけ）。
等号だと「係数 8 だと NO₃⁻ は 8個。2個 要る」と言って**正しい 8 を弾く** ＝ rn1・rn2 は⑥に
着けない。大小（`c.per * n < c.need`）で見るように直した。
★ 4ステージ時代は「連れてくるぶん」と「反応するぶん」が**別の種**（H₂SO₄ の H⁺ と SO₄²⁻）
だったので、この形が一度も踏まれていなかった。**5ステージを通した瞬間に初めて出た**。

正解のときの割り算も、**本数を決めているイオンだけ**を言うように直した
（NO₃⁻ 2個 ÷ 1個 ＝ 係数 8 という、合わない式を書いてしまうため）。

**(2) ④後半の「相手」に自分自身が混ざっていた**

`spectatorAddRows` の `partners` は「その物質が覆っている左辺のイオン」を全部並べていたので、

## 筆算1枚にまとめる（2026-09-10・レーン `rx-hissan2`）

ユーザーの指示（原文。ここが仕様の一次資料）:

> **ここを筆算に寄せたい**
> **イオン反応式の下に筆算形式で K+ と SO42- の入力欄を入れる、最後の係数も筆算の中に入れる**

> **ここもわかりやすくしたい**
> **・直前のイオン反応式との対応がわかりづらい**
> **・もともと何だった？に対してイオンと組み合わせる、は違和感**
>
> 改善案：筆算のイオン反応式の左辺のイオンをマーカーし、その下に、
> イオンがもともと何だったのカードをドラッグさせる

> **もともと何だったか、を正解した後に、改めてイオン反応式を出すようにしてください、
> 上下が離れるとわかりづらいです**

### 0. 3つの申し立ては1つに集約される ──「答えるとき、根拠が目に入っていない」

v205 は④前半（もともと何だった）・④後半（両辺に加える数）・⑤（左辺の係数）が
**縦に3つ並ぶだけ**で、根拠のイオン反応式（③）はいちばん上に1回出るきりだった。
900px 幅の ro1 で実測すると、③の合計行から⑤の入力欄まで **655px**。
＝ **答えを書いている場所から、根拠の式が画面の外に出ている。**

### 1. 決めた形 ── 式の左辺の項を「柱」にした1枚のグリッド

```
  ③で出したイオン反応式 — 左辺の項が、そのまま下の欄の見出しになる
    3 CH₃CH₂OH   ＋   Cr₂O₇²⁻   ＋   8 H⁺      → 3CH₃CHO ＋ 2Cr³⁺ ＋ 7H₂O
        ↓               ↓            ↓
    〔 CH₃CH₂OH 〕  〔 K₂Cr₂O₇ 〕 〔 H₂SO₄ 〕     ← ④前半（札を置く）
    ── 札の棚 ── [CH₃CH₂OH][K₂Cr₂O₇][H₂SO₄]
    3 CH₃CH₂OH   ＋   Cr₂O₇²⁻   ＋   8 H⁺       ← ★柱をもう一度
    両辺に ＋ K⁺〔2〕個ずつ ＋ SO₄²⁻〔4〕個ずつ    ← ④後半
    3 CH₃CH₂OH   ＋   Cr₂O₇²⁻   ＋   8 H⁺       ← ★柱をもう一度
    〔3〕CH₃CH₂OH  〔1〕K₂Cr₂O₇  〔4〕H₂SO₄       ← ⑤（左辺の係数）
```

★ **答えの置き場所そのものを、式の真下にした。** 縦の対応は言葉ではなく**位置**が言う。

### 2. 「上下が離れない」を (ア) 繰り返す／(イ) 貼り付ける のどちらで解いたか

**(ア) を採った。ただし「式ぜんぶ」ではなく「柱だけ」を刷り直す。**

| | 900px での実測（ro1・柱からその段の入力欄まで） |
|---|---|
| 前（v205・③の合計行から） | ④前半 **199px** ／ ④後半 **431px** ／ ⑤ **655px** |
| 後（柱を1回だけ・echo なし） | ④前半 **22px** ／ ④後半 **396px** ／ ⑤ **577px** |
| **後（echo あり・採用）** | ④前半 **22px** ／ ④後半 **77px** ／ ⑤ **69px** |

- **(イ)（画面の上に貼り付ける）は採らなかった。** 理由は2つ:
  1. **狭い画面で本文の場所を食う。** ion-equation の筆算は 320px で既に横送り寸前で、
     イオン反応式は 375px 幅だと 2〜3行になる（＝ 60〜90px ＝ 640px の高さの 10〜14%が
     ずっと埋まる）。この段は**入力欄が縦に積まれる段**なので、そこを削るのがいちばん痛い
  2. **列がそろわない。** 貼り付けた式は画面の上にあり、下の入力欄と**横の位置が合わない**。
     ユーザーの申し立ての本体は「対応がわかりづらい」なので、
     位置で対応を言えないなら (イ) は半分しか答えていない
- ★ **echo は「柱だけ」**（＋右端に「↑ もう一度、イオン反応式の左辺」の1行）。
  式の全文を3回刷ると画面が伸びて、かえって「離れる」ほうへ戻る。
  ro1 の実測で、echo 2本を足しても段の高さは **1368px → 1448px（＋80px）**しか増えない。

### 3. ④前半 ──「◯◯ と組む」という**言い回し**を消し、罠そのものは残す

### 4. 置き方は**タップ**にした（ユーザーの言葉は「ドラッグ」）

理由（この順で効く）:

1. **この家の流儀。** 同じ画面の⑥（`blocks.js` の `IonBlocks`）はイオンを **click** で
   足し引きする（`blocks.js:139` / `:189`）。`ion-equation/` にドラッグの実装は1つも無い
2. **iPad で使う画面だから**（`BUGNOTE_touch_ipad.md`）。HTML5 のドラッグはタッチで発火せず、
   Pointer で自前実装すると S2・S6 と同じ型の穴（判定線がポインタを握る／モードが取り残される）に入る。
   **ドラッグだけにすると、触りにくい人が詰む**
3. **縦の対応が本体で、置き方は手段。**「柱の下に札が並ぶ」形はタップでも同じに見える

置き方は2手のどちらでもよい: **柱をタップ → 札をタップ**／**札をタップ**（いちばん左の未回答へ入る）。
戻すのは札の ✕。⚠ **ドラッグは足していない**（②の理由が「足すだけ」でも効くため）。
ユーザーが「やはりドラッグで」と言うなら、Pointer で**タップと併存**させる形にする。

### 5. 狭い画面（≤560px）── 柱を横に並べず、イオンごとの塊にする

```
  ┌ Cr₂O₇²⁻    → 〔 札 〕┐
  ┌ 8 H⁺       → 〔 札 〕┐
```

★ 塊の中では**イオンのすぐ横に受け皿がある**ので、対応はむしろ近くなる。
（③の筆算が 560px で折り返すのと同じ判断 ＝ そろえた効果がとっくに無い所では、そろえない。）
⚠ 回帰テスト `CALC-A2` が、320×568 で **`.bworkScroll` の横はみ出しが 0** であることを見張る。

### 7. 実装して分かったこと（設計と違った点）

- **④後半だけは柱の列にそろえられない。** 足すイオンは種でまとめた数で、
  1種が2つの物質から来ること（rs1 の SO₄²⁻ は FeSO₄ と H₂SO₄ から 10＋8）も、
  1つの物質が2つの柱にまたがること（rn1 の HNO₃ は H⁺ と NO₃⁻）もある。
  ★ ユーザーの絵でも `＋ K⁺〔 〕個 ＋ SO₄²⁻〔 〕個` は**最下段の1行**になっていて、
  列にはそろっていない ＝ 絵のとおりで正しかった
- **⑤の係数は列にそろう**が、対応は1対1ではない。1つの物質が2列を担当するときは
  **左端の柱の下**に置き、1つの柱を2つの物質が担当するとき（rs3 の H⁺）は**縦に積む**。
  列を決めるのは `answerKey`（模範）で、**人が置いた札では決めない**
  —— 置き直すたびに列が動くと筆算が読めなくなる
- **判定文と手がかりは全幅の行へ逃がした。** 柱の列は 100〜160px しかなく、
  「そのとおり。K₂Cr₂O₇ は水にとけて…」を列の中に入れると1文字ずつ縦に折れる。
  どの柱の話かは行の頭の札（`.bwNoteIon`）が言う
