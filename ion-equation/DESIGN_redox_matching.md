# M6: 酸化剤×還元剤 組み合わせシミュレーターの設計（2026-08-06）

`ion-equation/DEVELOPMENT.md` ロードマップの **M6「自由組み立てモード」**の第1弾。
収録済みの14ステージを順に解くのではなく、**酸化剤と還元剤を自分で選んで組み合わせ、
反応するかどうかを確かめる**モード。着想は Gemini のレビュー
（`docs/PLAN_stage_nav_and_combinatorial_matching.md` 【フェーズ2】。**`docs/` は追跡外**の
手元メモなので、clone しただけの人の手元には無い）。本書はそれを実装可能な粒度に落とし、
**化学として言い切ってよい範囲**を決める ＝ .gitignore が言う「レビューから決まった方針は
追跡されるファイル側に書き写すこと」の実行にあたる。
**着想から変えた点（採らなかった案）は §8 に、判断を仰ぐ論点は §9 にまとめてある。**

設計の型は `ion-equation/DESIGN_redox.md`（半反応式×倍率）と
`ion-equation/DESIGN_battery_electrolysis.md`（電極を選ばせる＝発見学習）を踏襲する。
とくに B3 で決めた3原則をそのまま引き継ぐ:

- モデルは既存の枠を流用する（`HALF_REACTIONS` × `checkRedoxMultipliers` → `combineHalves`）。
  拡張は「データ追加」と「アニメ／画面の新規」に閉じる
- 判定は個数のみ。座標は見た目専用
- **判断できない反応は候補に出さない**

---

## 1. 何を解決するのか / 何を解決しないのか

### 解決すること

1. **「酸化剤」「還元剤」が物質の属性ではなく、相手との関係で決まる**ことを操作で体験させる。
   いまの14ステージは組み合わせが固定なので、この相対性が体験にならない
   （B3 が電池で「Cu は Zn と組めば正極、Ag と組めば負極」を見せるのと同じ狙いを、
   溶液中の酸化還元でやる）
2. **「反応しない」を、エラーではなく学習内容として返す**。なぜ起こらないかを、
   理由の種類ごとに言葉で説明する
3. 収録済み14ステージへの**入口を増やす**。自分で選んだ組み合わせがステージと一致したら、
   そのステージの解説へ橋を架ける

### 解決しないこと（非目標）

- **標準電極電位の数値を出すこと**。B3 §6 の非目標をそのまま継ぐ。
  数値を出すと「イオン化傾向の暗記」が「電位の暗記」にすり替わるだけで、高校範囲でも要求されない
- **反応の速さ・実際に観察できるかの判定**。梯子（§2）が語れるのは向きだけで、
  速いか遅いかは語れない。だから **「反応する」と言い切るのは教科書が扱う組み合わせに限る**（§2-5）
- **半反応式そのものをユーザーに組ませる練習**。`DESIGN_redox.md`「将来」に残る別テーマ
- **酸×塩基版**（Gemini 提案の3番）。§8-5 に採らなかった理由
- 電池・電気分解（B3 の担当）。自由組み合わせは**1つのビーカーの中**の話に限る

## 2. 組み合わせの判定モデル（本設計の核心）

### 2-1. 現物の棚卸し（憶測を混ぜないための出発点）

`ion-equation/model.js` を読んだ結果、いまあるもの／無いものは次のとおり。

| あるもの | 実体 |
|---|---|
| `HALF_REACTIONS` | **24本**。`{ disp, kind, left, right }`（`kind` は `"oxidation"` か `"reduction"`）。原子・電荷保存と e⁻ を含むことは既存テストが機械検証している |
| `kind` | **半反応式ごと**に酸化／還元が付いている。物質ごとではない（`Cu_ox` と `Cu_red`、`H2O2_red` が別々に立っている） |
| `electronsOf(hr)` | 授受する e⁻ の数 |
| `checkRedoxMultipliers(stage,a,b)` | e⁻ の数が合うか＋最簡整数比か |
| `combineHalves(stage,a,b)` | 倍率をかけて足し、両辺共通種を打ち消してイオン反応式にする |
| `OXIDATION` / `oxChangeOfHalf` | 原子ごとの酸化数と、その半反応式で変化した原子 |
| `REDOX_STAGES` | **14本**。`{ id, title, ox, red, answer:[a,b], mode?, intro, molecularEq?, cleavage? }` |

| 無いもの | 影響 |
|---|---|
| **酸化力・還元力の強さを表すデータが一切ない** | 「反応するか」を今のデータからは1ミリも導けない。ここが M6 の新規データの本体 |
| `IONIZATION_SERIES` | B3 で**設計はされたが未実装**（`model.js` に存在しない）。M6 はこれを金属限定ではなく一般化した形で先に入れる |
| 液性の情報 | ステージにも半反応式にも無い。ただし `left` に H⁺ があるか否かで**構造から導ける**（§2-4） |
| `I_ox`（2I⁻→I₂＋2e⁻） | `DESIGN_redox.md` の表には載っているが**未実装**。KI を還元剤に選ばせるなら要追加 |
| `H2O2_ox`（H₂O₂→O₂＋2H⁺＋2e⁻） | 同上・**未実装**。H₂O₂ の二役はこの設計の見どころなので要追加 |

酸化側の半反応式は14本、還元側は10本ある。ただし酸化側のうち
`iodoform_ox` / `acylRest_ox` / `formylRest_ox` は**切り離した断片**が出発点で、試薬として選べる物ではない。

### 2-2. 案A: 組み合わせを1つずつ手で書いた表

`MATRIX[oxId][redId] = { reacts, reason }` を人が全部埋める。

- **利点**: 1セルずつ人が化学の判断をするので、機械が勝手に結論を出さない。説明文も個別に書ける
- **欠点**:
  - **セル数が O(N²)**。いまの実装ぶんだけで 14×10＝**140セル**。試薬を1つ足すたびに列が丸ごと増える
  - **埋め忘れが「反応しない」と区別できない**。未記入セルを既定値で埋めた瞬間、
    書いていないことが断定になる（このリポジトリで最も避けたい事故の形）
  - 同じ原理（順位が逆）を140回書き写すので、**原理が表の中に散らばって消える**。
    「イオン化傾向」という1本の話が140個の独立した事実に化ける
  - 表の中で矛盾が起きても機械検査できない（A＞B・B＞C・C＞A を許してしまう）

### 2-3. 案B: 半反応式＋「強さの順位」から機械的に導く 【採用】

**採用する。** ただし「機械的に導く」の中身を、電位の数値ではなく**一次元の順位表（梯子）**にする。

```js
/* 酸化還元の梯子（酸性条件）。上にあるものほど「e⁻ を奪う力が強い＝酸化剤として強い」。
   値は**順位であって電位ではない**（10刻みなのは間に足せるようにするため）。
   同じ値＝この収録範囲では強弱を決めない（＝判定しない。§2-5 の3値目）。
   画面に数値そのものを出してはいけない（電位の暗記にすり替わる）。 */
const REDOX_LADDER_ACID = {
  "O3/O2":        200,   // O₃ ＋ 2H⁺ ＋ 2e⁻ → O₂ ＋ H₂O
  "H2O2/H2O":     190,   // H₂O₂ が酸化剤としてはたらくとき
  "MnO4-/Mn2+":   180,
  "Cr2O7^2-/Cr3+":170,
  "O2/H2O":       150,   // H2O_ox の対
  "NO3-/NOx":     130,   // 硝酸。希・濃で順位を分けない（§2-6・要判断）
  "Ag+/Ag":       120,
  "Fe3+/Fe2+":    115,
  "O2/H2O2":      110,   // H₂O₂ が還元剤としてはたらくとき。同じ物質が梯子に2回出る
  "I2/I-":        100,
  "Cu2+/Cu":       90,
  "H+/H2":         80,   // ここが「イオン化傾向で H より上か下か」の境目
  "Fe2+/Fe":       60,
  "CO2/C2O4^2-":   55,   // シュウ酸
  "Zn2+/Zn":       50,
  "Al3+/Al":       30,
  "Mg2+/Mg":       10,
};
```

- 梯子のキーは**半反応式の id ではなく「対（couple）」**。`Cu_ox` と `Cu_red` は
  向きが違うだけの同じ対なので、`HALF_REACTIONS` の各項に `couple: "Cu2+/Cu"` を足し、
  **梯子は couple → 順位** で引く。`Cu_ox` と `Cu_red` が同じ couple を指すことはテストで固定する
- 判定は1行:
  **`rank(酸化剤の対) > rank(還元剤の対)` なら反応が進む向き**。同値なら「判定しない」
- **イオン化傾向表は、この梯子から金属の対だけを抜き出したもの**になる。
  B3 が別に持とうとしていた `IONIZATION_SERIES` は、この梯子の部分集合として導出できる
  （`IONIZATION_SERIES = 梯子のうち "M^n+/M" 形の対を順位の低い順に並べたもの`）。
  B3 の実装が始まったらそちらから参照する ＝ **原理データを二重に持たない**

**利点**

- **データが O(N)**。試薬を1つ足すのは梯子に1行足すだけ。140セルが18行になる
- **矛盾が構造的に起こらない**。一次元の順位なので推移律が自動で成り立つ
- 「反応しない理由」が**1つの原理から生成される**ので、説明文がぶれない
- 既存14ステージが全部「反応する」と判定されることを**回帰テストで固定できる**
  （＝梯子が既存データと矛盾していないことの機械的な証明。案Aではこの検査が書けない）

**欠点と、その手当て**

| 欠点 | 手当て |
|---|---|
| 一次元の順位は、電位差がごく小さい対を無理に順序づけてしまう | **同じ値を許す**。同値＝「判定しない」。順位を付けられないものに順位を付けない |
| 有機の酸化（`EtOH_ox` 等）には高校で扱う順位が存在しない | **梯子に載せない**。有機の酸化剤は明示的な許可リスト（`pairsWith: ["Cr2O7_red","MnO4_red"]`）で相手を列挙する。ここだけは手書きの表が正しい（§2-7） |
| 順位が上でも実際には反応しないことがある（不動態など） | **例外表**（§2-7）。件数が少ないので O(数件) に収まる |
| 順位が上なら「必ず反応する」と機械が言い切ってしまう | 出力を3値にし、**「反応する」と言い切るのは収録した試薬の範囲内だけ**にする（§2-5） |

### 2-4. 液性の扱い — 「足りない」ではなく「別の式になる」

Gemini の例2「Cr₂O₇²⁻ は強酸性条件でのみ強い酸化力を発揮します。液性を『硫酸酸性』に
設定してください」は、**言い方として危うい**。MnO₄⁻ は中性・塩基性でも酸化剤として働き、
生成物が MnO₂ に変わるだけである（＝反応しないのではなく、**式が変わる**）。

そこで液性は次のように扱う。

1. **必要な液性は半反応式の形から導く**（機械的・追加データ不要）:
   - `left` に H⁺ を含む → 酸性が必要（`MnO4_red` `Cr2O7_red` `NO3_red` `O3_red` `H2O2_red` …）
   - `left` に OH⁻ を含む → 塩基性が必要
   - どちらも無い → 液性に依らない（`Zn_ox` `Cu_red` `Ag_red` `I2_red` …）
   - これは**必要条件であって十分条件ではない**。「H⁺ が無いからこの式では起こらない」までは
     言えるが、「だから何も起こらない」とは言えない
2. だから中性・塩基性を選んだときの返答は
   **「この式は酸性条件のもの。中性・塩基性では別の半反応式になる」**にする。
   別の式を収録していれば差し替えて動かし、収録していなければ「このアプリは未収録」と正直に言う
3. 収録するなら追加する半反応式（M6-D）:

   | id | 半反応式 | 備考 |
   |---|---|---|
   | `MnO4_red_neutral` | MnO₄⁻ ＋ 2H₂O ＋ 3e⁻ → MnO₂ ＋ 4OH⁻ | 中性・塩基性。MnO₂ は黒褐色の沈殿＝色の見どころ |

   `condition.html`（液性で書き換えるモード）は
   **「同じ酸化還元を書き換えただけ」**の場合しか扱わないと明記している（`toBasicHalf` の注記）。
   MnO₄⁻ の塩基性形は**別の半反応式**なので `CONDITION_STAGES` には入れず、M6 側で持つ。
   この線引きは既存コメントに書かれているとおりで、破らない

### 2-5. 出力は3値にする（Gemini 案からの最大の変更点）

Gemini のスケッチは「反応する／エラー」の2値だが、**2値にすると必ず嘘をつく**。
判断できないものを「反応しない」に寄せれば嘘、「反応する」に寄せれば嘘になる。

```js
/* matchRedox() の返り値 */
{
  verdict: "reacts" | "no-reaction" | "undecided",
  reasonCode: "...",        // no-reaction / undecided のときは必ず入る（enum）
  message: "...",           // 学習者に見せる説明文
  stage: { ox, red, answer, mode } | null,   // reacts のとき、既存エンジンに渡せる合成ステージ
}
```

- `reacts` … 反応する。段1以降（既存の倍率合わせ）へ進める
- `no-reaction` … **理由が言える**ときだけ。理由コードは下表の3つに限る
- `undecided` … 順位が同じ／梯子に無い／液性の式が未収録。**「判定しない」と正直に言う**。
  これを潰さないことが「正しさ最優先」の実装上の中身

### 2-6. 「反応しない」理由の種類（enum。この4つ＋1で全部）

| コード | いつ出るか | どう判定するか | 学習者に見せる文（案） |
|---|---|---|---|
| `same-role` | 両方とも酸化剤／両方とも還元剤 | `kind` が同じ | 「どちらも **e⁻ を受け取る側**の式です。e⁻ を出す相手（還元剤）を選ぼう」 |
| `ladder-reversed` | 順位が逆 | `rank(ox) < rank(red)` | 「Cu²⁺ は Ag より e⁻ を奪う力が弱いので、Ag から e⁻ を奪えません。順位は Ag⁺ ＞ Cu²⁺」 |
| `wrong-condition` | 選んだ液性でその式が成り立たない | §2-4 の構造導出 | 「この式は酸性条件のもの。中性・塩基性では **別の式**（MnO₄⁻→MnO₂）になります」 |
| `exception` | 例外表に載っている | 例外表を引く | 「Al は濃硝酸に入れると表面に緻密な酸化被膜（不動態）ができ、それ以上溶けません」 |
| （`undecided`） | 上のどれでもなく反応もしない | 梯子の同値・未収録 | 「この組み合わせは、このアプリでは強弱を決めていません」 |

**`same-role` の言い方に注意**。`H2O2` も `Fe^2+` も相手しだいで役が変わるので、
**「H₂O₂ は酸化剤です」と物質を主語にした断定を出してはいけない**。主語は必ず「いま選んだ式」にする。
むしろ H₂O₂ を選んだときに「この物質は梯子に2回出てくる」と見せられるのが、このモードの見どころ。

**Gemini の例3「イオン化傾向の差が小さいため、この条件では著しい反応が進行しません」は採らない。**
高校範囲では**差の大小ではなく順序**で決まる。差が小さくても順序が正しければ反応は起こる
（そこから先は平衡・速度の話で、高校では扱わない）。この文は生徒に誤った因果を教えるので、
`ladder-reversed` の説明では「順序が逆だから」とだけ言う。

### 2-7. 梯子で語れないものは、正直に列挙する

一次元の梯子で扱えないものが2種類ある。ここだけは**手で書いた表**が正しい。

```js
/* (a) 有機の酸化。高校で扱う順位が存在しないので、相手を明示列挙する */
const ORGANIC_OXIDANTS = {
  "EtOH_ox":   ["Cr2O7_red", "MnO4_red"],
  "MeCHO_ox":  ["Cr2O7_red", "MnO4_red"],
  "iPrOH_ox":  ["Cr2O7_red", "MnO4_red"],
};

/* (b) 例外表。順位では「反応する」になるが、実際には起こらない組み合わせ。
   件数が少ないので対で持つ。理由文は必須（理由が書けないものは載せない）。 */
const REDOX_EXCEPTIONS = [
  { ox: "NO3_red_conc", red: "Al_ox", code: "passivation",
    message: "Al は濃硝酸に入れると表面に緻密な酸化被膜ができ（不動態）、それ以上は溶けません。" },
  { ox: "NO3_red_conc", red: "Fe_ox", code: "passivation", message: "…" },
];
```

`qa/KNOWLEDGE_CAVEATS.md` の該当項目を必ず読んでから足す:

- **H-2 濃硫酸**: 酸化作用を示すのは**熱濃硫酸だけ**。冷濃硫酸は Al・Fe・Ni と不動態。
  → いまは H₂SO₄ の酸化剤としての半反応式を**持っていない**。M6 で足すなら
  「熱濃硫酸」と明記した試薬として足す（「濃硫酸」という札は使わない）。M6-C 以降の判断事項
- **H-3 過酸化水素の還元剤としての相手**: 実質 KMnO₄ と O₃ のみ。
  → 梯子で `O2/H2O2`（110）より上にある対は O₃・H₂O₂(酸化側)・MnO₄⁻・Cr₂O₇²⁻・O₂/H₂O。
  Cr₂O₇²⁻ は「一部条件」なので、**梯子の順位だけで H₂O₂×Cr₂O₇²⁻ を playable にしない**。
  §2-5 の「試薬の範囲内でだけ反応すると言い切る」で絞る
- **H-1 クロム酸⇄二クロム酸**: これは酸化還元ではない。CrO₄²⁻ を試薬に加えない
- **G-6 ボルタ電池の分極**: 過電圧が効く系は候補に出さない（B3 §6 と同じ）

### 2-8. どこまで言い切ってよいか（方針のまとめ）

1. **数値（標準電極電位）は持たない・出さない**。順位だけを持つ
2. **順位表を「表」として学習者に見せるかは要判断**（§9-2）。少なくとも
   「これは高校で扱う範囲での相対順位であって、暗唱表ではない」と添える
3. **「反応しない」と断定するのは、理由コードが付く4種類だけ**。それ以外は「判定しない」
4. **「反応する」と断定するのは、収録した試薬どうしの組み合わせだけ**。
   梯子は無限に外挿できてしまうので、選択肢の側で範囲を切る
5. 収録する試薬は**教科書の「主な酸化剤・還元剤」の表に載るもの**に限る。
   これが「教科書が扱う組み合わせ」という線引きの実体になる

## 3. 既存14ステージとの関係（データを二重に持たない）

### 3-1. 置き換えない。併存させる

`REDOX_STAGES` の14本は**解説つきの決まった道**（`intro`・`molecularEq`・`cleavage` を持つ）。
自由組み合わせは**道のない砂場**。役割が違うので併存させ、ステージ帯（1〜14）はそのまま残す。

### 3-2. 合成ステージ — 同じ形のオブジェクトを実行時に作る

既存エンジン（`redox.js`）はステージを `{ ox, red, answer, mode }` の形でしか見ていない。
だから自由組み合わせは**同じ形のオブジェクトをその場で組み立てて渡す**だけでよい。
`redox.js` 側の改修は「ステージの出どころ」を差し替える1点に閉じる。

```js
/* 半反応式2本から、REDOX_STAGES と同じ形のステージを合成する（純ロジック） */
function composeStage(oxId, redId) {
  const ox = HALF_REACTIONS[oxId], red = HALF_REACTIONS[redId];
  const eO = electronsOf(ox), eR = electronsOf(red);
  const l = eO * eR / gcd2(eO, eR);            // e⁻ の最小公倍数
  return {
    id: `free:${oxId}+${redId}`,
    title: `${dispOf(oxId)} × ${dispOf(redId)}`,
    ox: oxId, red: redId,
    answer: [l / eO, l / eR],                  // 持たずに導く
    mode: metalSourceOf(ox) ? undefined : "solution",   // 持たずに導く
    intro: "…",
  };
}
```

- **`answer` を導出にする**のが要点。既存14本は `answer` をデータで持っているが、
  それは最小公倍数から一意に決まる。
  **導出値が既存14本の `answer` と全部一致することをテストで固定する**（§6）。
  一致しなくなったら、どちらかのデータが壊れている
- **`mode`（板あり／溶液中）も導出する**。判定は「酸化側の出発種が
  電荷0・元素1種・気体でない＝金属板として置ける」かどうか（`redox.js` の `isDepositable`
  と同じ考え方）。これも14本の登録値と一致することをテストで固定する
- `molecularEq` / `cleavage` は合成しない。`redox.js` の `updateSheetTail` は
  `molecularEq` が無ければ段④⑤を出さない作りなので、**無改修で「段③まで」になる**
  （rs1〜rs3・ri1〜ri2 が既にその状態）

### 3-3. 収録ステージへの橋（対応表は書かない）

選んだ組み合わせが収録ステージと同じなら「解説つきのステージがあります」と案内する。
このとき **`(oxId, redId) → ステージ` の対応表を書かない**。`REDOX_STAGES` を実行時に走査して
`ox`・`red` が一致するものを拾う。理由はリポジトリの既定方針と同じで、
対応表を別に持つと収録を変えたときに黙って壊れるから
（`ion-equation` ↔ `ratio` の横断で「対応表は書かない・式の照合で引く」と決めた v114 の考え方）。

なお**同じ (ox, red) を持つステージが複数ある**（ri1 と ri2 は
どちらも `iodoform_ox`×`I2_red`）。だから引くのは**1件ではなく一覧**にする。
横断リンクで「対応表は代表1件しか持てないから式で照合する」と決めたのと同じ失敗が、
ここでも起きる。

  **横に並べない**（Gemini のスケッチは3カラムだが、320px では成立しない）

### 4-3. 結果の見せ方

| verdict | 画面 |
|---|---|
| `reacts` | 段0が「選んだ組み合わせ」の要約に畳まれ、**段1（半反応式2本）以降が現れる**。以後は既存の体験とまったく同じ |

### 5-1. 追加するデータ

|---|---|

### 5-2. `REAGENTS`（試薬 → 半反応式の索引）

```js
/* 選択肢に出す試薬。1つの物質が液性・濃度で違う半反応式になるので、ここで解決する。
   ここに無い物質は選べない ＝ §2-5「収録した範囲でだけ言い切る」の実体。 */
const REAGENTS = [
  { id: "KMnO4", sp: "KMnO4", side: "ox",
    half: { acid: "MnO4_red" },              // 中性・塩基性は M6-D で MnO4_red_neutral
    note: "赤紫色。酸性で最も強い酸化剤の代表" },
  { id: "K2Cr2O7", sp: "K2Cr2O7", side: "ox", half: { acid: "Cr2O7_red" } },
  { id: "HNO3_dil",  sp: "HNO3", side: "ox", half: { acid: "NO3_red" },      variant: "希" },
  { id: "HNO3_conc", sp: "HNO3", side: "ox", half: { acid: "NO3_red_conc" }, variant: "濃" },
  { id: "H2O2_ox",   sp: "H2O2", side: "ox", half: { acid: "H2O2_red" } },
  { id: "H2O2_red",  sp: "H2O2", side: "red", half: { acid: "H2O2_ox" } },   // 同じ物質が両側に出る
  { id: "HCl_dil",   sp: "HCl",  side: "ox", half: { acid: "H_red" }, note: "酸化剤としてはたらくのは H⁺" },
  ...
  { id: "Zn", sp: "Zn", side: "red", half: { any: "Zn_ox" } },   // 液性に依らない
];
```

- `side` は `HALF_REACTIONS[half].kind` から**導けるので持たない**、という選択もあるが、
  **持って、`kind` と一致することをテストで固定する**ほうがよい。
  データの書き間違い（酸化剤の欄に還元剤を並べる）が機械で止まる
- `H2O2` が **`side: "ox"` と `side: "red"` の両方に出る**のがこの設計の見どころ。
  UI では「過酸化水素（酸化剤として）」「過酸化水素（還元剤として）」と書き分ける
- **HCl / H₂SO₄ を「酸化剤」の欄に置くのは正しい**（酸化剤の本体は H⁺）。
  ただし札には「うすい塩酸（酸化剤としてはたらくのは H⁺）」と添える。
  ここを黙って `H⁺` と書くと、学習者が手に持つ物と対応しなくなる

### 5-3. 判定関数

```js
/* 純ロジック。DOM を触らない。返り値は §2-5 の形 */
function matchRedox(oxReagentId, redReagentId, condition /* "acid" | "basic" */) { … }
```

判定の順序（**先に出た理由で確定する**。順序自体が「どの理由を優先して見せるか」の設計判断）:

1. `side` が同じ → `same-role`
2. 液性でその試薬の半反応式が解決できない → `wrong-condition`
3. 例外表に載っている → `exception`
4. 有機の酸化（`ORGANIC_OXIDANTS` に載る）→ 相手が許可リストにあれば `reacts`、
   無ければ `undecided`（**`no-reaction` にしない**。順位を持っていないので「しない」と言えない）
5. 梯子に両方の対がある → 順位で `reacts` / `ladder-reversed` / 同値なら `undecided`
6. どちらかが梯子に無い → `undecided`

## 8. 採らなかった案

1. **組み合わせを1つずつ手で書いた表（Gemini 案そのまま）** — §2-2。
   140セルの人手・埋め忘れが断定に化ける・原理が表の中で消える・矛盾を機械検査できない
2. **標準電極電位の数値を持ち、差で判定する** — `DESIGN_battery_electrolysis.md` §6 の
   非目標と正面から衝突する。数値は高校範囲で要求されず、序列の暗記が電位の暗記に
   すり替わるだけ。加えて E° は熱力学しか語らないので、**数値を出すと
   「差があるのに反応しない」（不動態・過電圧）を説明できなくなる**
3. **「イオン化傾向の差が小さいので反応しない」という説明**（Gemini 例3） — §2-6。
   高校範囲では差の大小ではなく順序で決まる。誤った因果を教える
4. **出力を2値（反応する／エラー）にする** — §2-5。「判定しない」を潰すと必ず嘘になる
5. **酸×塩基版を同じ画面に同居させる**（Gemini 提案の3番） — 強弱の原理が違う
   （酸化還元は e⁻ の梯子、酸塩基は H⁺ の受け渡しやすさ）。同じ UI に混ぜると

   なお酸塩基側は `index.html`（イオン反応モード）に土台があり、
   `WEAK_ELECTROLYTES` / `WATER_IONIZATION` という別のデータを既に持っている
6. **`redox.html` とは別のページを新設する** — §4-1。ビーカーも筆算も同じなので、
   ページを分けると `redox.js` を丸ごと写すことになる
7. **合成ステージを `REDOX_STAGES` に事前展開して持つ** — 組み合わせの数だけ
   ステージが増え、`answer` を人が書くことになる（§3-2 の導出と真逆）。

8. **濃硝酸・希硝酸に順位の差を付ける** — §9-1 のとおり教科書の言い方と E° の順序が逆で、

## 9. ユーザーに判断を仰ぐ論点

### 9-1. 濃硝酸と希硝酸、どちらを「酸化力が強い」とするか 【最重要】

教科書は「濃硝酸のほうが酸化力が強い」と教えるが、標準電極電位では
**希硝酸（NO₃⁻/NO ＝ +0.96 V）のほうが濃硝酸（NO₃⁻/NO₂ ＝ +0.80 V）より高い**。
教科書の言い方は濃度効果を「酸化力」と呼んでいるもので、一次元の梯子には乗らない。

- **本設計の暫定案**: 硝酸は**1つの対**として同じ順位に置き、希・濃の違いは
  「順位」ではなく「**生成物が変わる**（NO ⇄ NO₂）」でだけ表す（既存 rn1/rn2 の見せ方と同じ）
- 判断が要る: この扱いでよいか。「濃硝酸のほうが強い」と画面で言う場面を作るか、
  作らないか。作るなら `qa/KNOWLEDGE_CAVEATS.md` に1項目起こすべき内容

### 9-2. 順位表（梯子）を学習者に見せるか

見せると判定の根拠が分かるが、**新しい暗唱表を1つ増やす**ことになる。
見せないと「なぜ反応しないと言えるのか」がブラックボックスになる。

- 折衷案: **全体の表は出さず、判定に使った2つの対だけを「梯子の一部」として抜き出して見せる**
  （「Ag⁺ ＞ Cu²⁺」の2行だけ）。イオン化傾向表の暗記に置き換わらない
- 判断が要る: この折衷でよいか、全体表も見られるようにするか

### 9-3. 収録する試薬の線引き

M6-A の提案は「教科書の『主な酸化剤・還元剤』の表に載るもの」。具体的には
酸化剤＝KMnO₄・K₂Cr₂O₇・希硝酸・濃硝酸・H₂O₂・I₂・O₃・希塩酸(H⁺)・CuSO₄・AgNO₃、
還元剤＝Mg・Zn・Fe・Cu・FeSO₄・シュウ酸・KI・H₂O₂。

- 判断が要る: **熱濃硫酸**を入れるか（入れるなら半反応式1本の追加と、
  `KNOWLEDGE_CAVEATS` H-2 のとおり「熱」の明記が必須）
- 判断が要る: **SO₂・H₂S** を入れるか（SO₂ は H₂O₂ と並ぶ「二役」の代表で教育価値が高いが、
  半反応式2本と種の追加が要る）

### 9-4. 中性・塩基性を選べるようにするか（M6-D をやるか）

`MnO4_red_neutral`（MnO₄⁻＋2H₂O＋3e⁻→MnO₂＋4OH⁻）は高校範囲の上限に近い。
入れると「液性で式が変わる」を実装で示せるが、収録範囲が広がる。

- 判断が要る: M6-D をやるか。やらない場合、液性の選択肢自体を出さない
  （出して「未収録」と返すより、**選べないほうが正直**という考え方もある）

### 9-5. 不動態を「反応しない」と言い切ってよいか

`KNOWLEDGE_CAVEATS.md` H-2 は不動態を事実として書いている（＝言い切ってよさそう）。
ただし「表面だけが反応して止まる」ので、厳密には「まったく反応しない」ではない。

- 判断が要る: `exception` の文面を「反応しません」にするか
  「**表面に被膜ができて、そこで止まります**」にするか。後者を推奨

### 9-6. 「判定しない」ペアを選択肢に出すか

`undecided` を返すくらいなら、**その組み合わせを最初から選べなくする**（片方を選んだ時点で
相手の `<select>` から外す）ほうが親切、という考え方がある。
一方で「選べないこと」自体が理由の説明にならないので、選ばせて説明する価値もある。

- 判断が要る: 選ばせて `undecided` を返すか、選択肢から外すか。
  B3 §0 の「判断できない反応は候補に出さない」に厳密に従うなら後者

### 9-7. 入口をどこに置くか

`modeBar` にリンクを1本足す案（§4-1）でよいか。
`memory` の「入口（導線）の見直し」（chem-entry-points-review）で
**新機能の入口は作り込まない・全体でまとめて見直す**という方針があるので、
M6-B ではリンク1本だけにとどめ、`portal.html` / `library.html` への露出は
入口の全体見直しに合流させる、という進め方を提案する。
