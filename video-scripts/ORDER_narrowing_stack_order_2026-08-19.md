# 発注（Assembler レーンへ）: 絞り込みモードが「条件の順番」をどう取り込んでいるか

**2026-08-19・動画レーンから。** V99（構造決定シリーズ①）の収録中に見つけた。

> ⚠ **これは「東大の1件を直して」という発注ではない。**
> **なぜそうなったのかを先に知りたい**、という発注。原因を見ないまま1件だけ直すと、
> **同じ状態の問題が他にも埋まったまま見えなくなる**。

## 1. 見つけたこと

`assembler/narrowing-problems.json` の東大2021前期1I:

```json
{"id":"2022-東京大学-1I", "columns":[
  {"name":"B", "stack":["carbonyl-no","na","br2-no","ox2","iodo"], "expect":3},
  {"name":"B′","stack":["iodo","ring-yes","ring4"], "expect":1}]}
```

**問題文の実験**（ユーザー確認・2026-08-19）:

| 実験 | 内容 | 対応する述語 |
|---|---|---|
| 1 | ナトリウムと反応 | `na` |
| 2 | **水素付加** | **`h2-no`** |
| 3 | アルコールの酸化 | `ox2` |
| 4 | ヨードホルム | `iodo` |
| 5 | カルボニル（赤外） | `carbonyl-no` |
| 6〜8 | オゾン分解ほか | **B には関係しない** |

**食い違いは2つある。**

- **順番**: `carbonyl-no` が先頭にあるが、問題では**5番目**
- **札そのもの**: `br2-no`（臭素水）を使っているが、問題は**水素付加**（`h2-no`）

## 2. 先に調べてほしいこと（ここが本題）

生成は `_解析/tools/build-narrowing-data.js` のはず。

1. **`stack` の順番は何で決まっているか。** 問題文の実験の順を**そもそも取り込んでいるのか**、
   それとも述語IDの都合（定義順・アルファベット順・出現順など）で並んでいるだけか
2. **`br2-no` はなぜ選ばれたか。** 水素付加の述語を**当てられなかった**のか、
   **同値と見なした**のか。前者なら述語の対応表の穴、後者なら**判定の誤り**（下の 4 を参照）
3. **他の問題も同じ状態になっていないか。** 東大だけの事故か、生成の仕様か

## 3. そのうえで「順番を持つべきか」を決めたい

ユーザーの見立て（そのまま）:

> 問題文の条件を任意の順に並べたらどうなるか、最短の順番が何か、を把握するのであれば
> 問題文の条件の順番は無くてもよいかもしれません

**実際、画面はすでに順番を総当たりで評価している。** 5枚積んだ状態でこう出る:

> 3通りに届く最小の組み合わせは**1つだけ**でした（いま 5 手、**最短 2 手**）。この筋以外に道はありません。

つまり **`stack` の順番の価値は「問題文どおりに再現すること」ではなく、
「順番で効きが変わることを見せること」**にある。だとすると選択肢は:

- **(A)** `stack` を問題文の順に正す（再現性を取る）
- **(B)** `stack` は**集合**として持ち、**並べる順はアプリが決める**（既定＝最短。切り替えで問題文順）
- **(C)** 両方持つ（`stack` ＋ `stackOrder: "problem" | "shortest"`）

**動画レーンとしては (B) か (C) が筋に見える**が、**生成側の事情を見てから決めてほしい**。
(A) だと「問題文の順」を人手で入れ続けることになり、問題が増えるたびに同じ事故が起きる。

## 4. 札の取り違えは、順番とは別の話（こちらは中身の誤り）

`br2-no` と `h2-no` は**強さが違う**。

| 述語 | 落とすもの |
|---|---|
| `br2-no`（臭素水を脱色しない） | C=C だけ |
| `h2-no`（水素を付加しない） | C=C・**ケトン**・**アルデヒド** |

**答えが変わる。** 実測（同じ5枚・順だけ問題文どおりに直したもの）:

| 使う札 | 数字 | 必須 | 最短 |
|---|---|---|---|
| `br2-no`（いまのデータ） | 55→51→26→8→5→3 | 2枚 | **3手** |
| **`h2-no`（問題文どおり）** | 55→26→8→5→3→3 | 2枚 | **2手** |

さらに `h2-no` の順だと、**実験5（`carbonyl-no`）で画面が「減らない」と表示する**——
実験2 の時点で C=O が消えているため。**これは正しい挙動**で、
「必須は2枚」という判定の**画面上の証拠**になっていて教材として強い。

**順番の議論と独立に、札は直す必要がある。**

## R-1. 順番は何で決まっているか — **仕様ファイルの `steps` の並び順そのまま**

`build-narrowing-data.js` の該当箇所はこれだけ:

```js
(t.steps || []).forEach((s, j) => { translate(s.test, out, ...); });   // 出た順に out.cards へ push
columns.push({ name, label: t.label, stack: out.cards, expect: t.expect });
```

**並べ替えは一切していない。** 定義順でもアルファベット順でも出現頻度順でもなく、
**`_解析/db/narrowing/<問題>.json` の `targets[].steps[]` に人が書いた順**が、そのまま `stack` になる。

### では仕様のほうは問題文の順を取り込んでいるか — **番号は持っているが、守っていない**

`2022-東京大学-1I.json` の `steps` は、`label` に実験番号を書いたうえで**この順**に並んでいる:

| steps の位置 | label の冒頭 | test（＝ stack に入る札） |
|---|---|---|
| 1 | 前提: 不斉炭素をちょうど1個 | `{chiral:1}` ＋ `asConstraint` → **制約パネルへ**（stack に入らない） |
| 2 | **実験5**: カルボニル基が無い | カルボニルなし → `carbonyl-no` |
| 3 | **実験1**: −OH をもつ | ヒドロキシ基あり → `na` |
| 4 | **実験2**: 水素付加しない＝環 | **炭素間二重結合なし → `br2-no`** |
| 5 | **実験3**: 酸化してケトン＝第二級 | 第二級アルコール → `ox2` |
| 6 | **実験4**: ヨードホルム陽性 | ヨードホルム陽性 → `iodo` |

つまり**問題文の順番の情報は仕様に書いてある**（`label` の「実験N」）。
**それを無視して並べたのは人**で、生成器はその並びを正直に運んだだけ。
そして **`label` は step 単位では出荷 JSON に一切載らない**（載るのは `targets[].label` ＝ 列の見出しだけ）
ので、**アプリ側には実験番号が1文字も届いていない**。

⚠ **これが「見えなくなる」の正体**: 出荷 JSON だけを見ても、順番が問題文どおりかは**原理的に判定できない**。

### 順番を崩した理由も、同じ仕様ファイルから読める（＝ 意図的）

`carbonyl-no` を先頭へ動かしたことと `br2-no` を選んだことは**別々の事故ではなく、1つの操作**。

- `h2-no`（水素を付加しない）は C=C・ケトン・アルデヒドを落とす
- `br2-no`（臭素水を脱色しない）は C=C しか落とさない
- **だが C=O をあらかじめ消してあれば、この2枚は同じ働きになる**

だから `carbonyl-no` を1枚目に上げてから `br2-no` を置いた。step の label が
「実験2: **水素付加しない＝環**」と、実験ではなく**そこから引き出した結論**を書いているのがその証拠。
**最終値は正しく 3 になる**（実測で確認）ので、検算 `expect === got` も素通りする。

### 札を取り違えた直接の原因 — **語彙の穴。`h2-no` を指す述語が存在しない**

述語対応表 `_解析/tools/narrowing-predicates.js` の `MAP` は **51 述語 / 49 札**。
アプリの 58 札のうち、`{chiral}` `{ring:N}` で直接扱う 8 枚を除いて
**述語からたどり着けない札は 2 枚だけ**:

> **`h2-no` と `branched`**

⚠ **つまり仕様は「水素を付加しなかった」と書きたくても書けない。**
書けないから、いちばん近い `炭素間二重結合なし` に畳み、畳んだぶんを順番の入れ替えで補った。
実際 **`h2-no` は全 19 問 50 列のどこでも一度も使われていない**（後述の [A]）。

## R-3. 直すとしたらどこを直すか

### どこを直すか — **出荷 JSON を手で直すのは不可**

- `assembler/narrowing-problems.json` は **`JSON.stringify` そのまま＝改行ゼロの1行**（13,447 バイト）。
  再生成した文字列と**バイト単位で一致**することを確認した（＝不動点）
- ⚠ **したがって差分は、何を直しても必ず `1 1`。** 東大の1文字を直しても、全問を作り直しても、
  `git diff --numstat` は同じ `1 1`。**CLAUDE.md の「84,890 行の差分でレビューが成立しない」の裏返しで、
  こちらは「1行の差分で何も見えない」**。どちらも人のレビューが効かない形
- 直す場所は **`_解析/db/narrowing/2022-東京大学-1I.json` の `targets[0].steps`**（順番）と、
  **`_解析/tools/narrowing-predicates.js` の `MAP`**（`水素付加しない: { card: 'h2-no' }` を足す）
- ⚠ **生成器の `APP` は本体の作業ツリーへの絶対パス直書き**（`build-narrowing-data.js` 19行目）。
  worktree からは `--write` してはいけない（本体側の `assembler/` を上書きする）

### 作り直すと差分はどれだけ出るか

**`1 1`。** ただし内容としては、**その回に触った問題以外は1バイトも変わらない**ことを
`JSON.stringify` の不動点性から保証できる。**問題は差分の大きさではなく、差分が読めないこと**。
守りが要るなら、
`narrowing-problems.json` を **1問1行**（`compounds.json` と同じ作法）にして
`verify-compounds.js` の検査0の仲間に入れるのが素直。
⚠ **いまこのファイルは機械の見張りが1つも掛かっていない**:
`verify-compounds.js` は見ていないし、`narrowing.js` が `fetch('narrowing-problems.json', {cache:'no-cache'})`
で読むので **`?v=` が無く `verify-release.js` の対象外**。

**② 順番だけ問題文どおり** `na > br2-no > ox2 > iodo > carbonyl-no`

| # | カードの文言 | 効き | 残り |
|---|---|---|---|

| 4 | ヨウ素と水酸化ナトリウムで黄色の沈殿が生じた | −2 | 3 |
| 5 | 赤外吸収でカルボニル基が見られなかった | **減らない** | 3 |

> 他にも解き方があります。3 通りに届く最小の組み合わせが **3 通り**ありました（いま 5 手、最短は **3 手**）。

**③ 順番も札も問題文どおり** `na > h2-no > ox2 > iodo > carbonyl-no`

2枚目が「**水素を付加しなかった**」に変わる。**数字は ② と1つも変わらない**（26→8→5→3→3）。変わるのは結論:

> 3 通りに届く最小の組み合わせは**1つだけ**でした（いま 5 手、最短 **2 手**）。この筋以外に道はありません。

**⚠ 発注書 §4 の表を1点だけ精密化する。**
「札を替えると 55→51→… が 55→26→… になる」のではなく、**2つの効果は分離できる**:

| 直すもの | 変わるもの | 変わらないもの |
|---|---|---|
| **順番だけ** | 途中の数（51→26 が 26 から始まる）・**5枚目に「減らない」バッジが出る** | 最終値 3・最短 3手・ルート 3通り |
| **札だけ**（`br2-no`→`h2-no`） | **最短 3手→2手・ルート 3通り→1通り**・「この筋以外に道はありません」 | 途中の数（この問題では `na` が1枚目にある限り同一） |

理由: C6H12O は O が1個なので、`na`（−OH をもつ）を通した時点で C=O は消えている。
そこから先では `br2-no` と `h2-no` は同じ働きになる。**`br2-no` が弱いことが露出するのは
`na` より前に置いたときだけ**で、いまのデータはまさにそこを避ける並びになっている。

⚠ **順番はユーザーがいつでも変えられる**（`#nw-stack` の各行に ↑↓ とドラッググリップがある。
`DESIGN_narrowing_mode.md` §1「カードの順番を入れ替えられること。効きの違いが見えるのが本体」）。
**つまり `stack` の順番は「初期表示の順」でしかない** ＝ 発注書の (B)（集合として持ちアプリが並べる）で
失うものは「最初に見える並び」だけ。

## R-4. 結論 — **入力ミスではない。生成の仕組みが構造的に落としている**

**1件の入力ミスではない。**根拠は4つ:

1. **仕様は実験番号を持っていた**（`label` の「実験5」「実験1」…）。
   **持っていた情報を、生成器が step 単位では1つも出荷しない。**
   ＝ 出荷データからは「問題文の順か」が**原理的に検証できない**構造になっている
2. **順番の入れ替えと札の取り違えは、独立した2つのミスではなく1つの操作。**
   弱い札（`br2-no`）を成立させるために `carbonyl-no` を先頭へ上げた。
   だから**最終値は正しく 3 になり、生成器の検算 `expect === got` を素通りする** ＝ 検算はこの種の
   食い違いに対して**構造的に無力**
3. **札の取り違えの直接原因は語彙の穴。** 述語対応表からたどり着けない札は
   `h2-no` と `branched` の2枚だけで、**そのうち `h2-no` がまさに必要だった**。
   `h2-no` は全 19 問で一度も使われていない。同じ穴を踏んだ step は**もう1件ある**（熊本大3 / D）
4. **回帰テストが誤りを正解として文書化していた。** `assembler/tests.js` の NW5 ③ は
   > `// ③ narrowing-problems.json が持つ B の実験列（順番は問題文どおり）でも 3。`
   > `// …デモ順は 11 から、問題文順は 51 から`

   と書いている。**51 から始まるのは問題文順ではなくデータの順**（問題文順は 26 から）。
   ⚠ **テストの主張が誤っているので、テストを見ても気づけない。**
   このコメントは順番を直すときに必ず一緒に直すこと

**したがって、東大の1件だけ直しても同じ状態は残る**（判定できない 71 target・語彙の穴を踏んだ
もう1件・見張りゼロの出荷ファイル・誤りを正解と書いたテスト）。
