## A-3.【バグ・再現した】番号①がまとめて下側に出る

### 原文

> **書き出し中、化合物の番号①がまとめて下側に表示されることがある**

### 再現条件（**`🧹 並べ直す` を押したあと**）

**答案を並べ直したときにだけ起きる。**自分で描いた（間隔の空いた）配置では起きない。

**実測（1280×800・v1428・C₄H₁₀O の異性体を N 個キャンバスに置き、`🧹 並べ直す` を押したあと、
見出しの実際の y と「既定の置き場所」の差を測った）**

| 成分の数 | 並べ直し | ずれた見出しの数 | 最大のずれ |
|--:|---|--:|--:|
| 7 | なし | **0** / 7 | 0 |
| 7 | **あり** | 2 / 7 | −6マス（上へ） |
| 10 | なし | 0 / 10 | 0 |
| 10 | **あり** | **5** / 10 | **+6マス（下へ）** |
| 16 | あり | 9 / 16 | +10マス |
| **20** | なし | 0 / 20 | 0 |
| **20** | **あり** | **10** / 20 | **+12マス（＝504px 下）** |

**20個のときの実際の並び**（抜粋。分子は 4行×5列 に並んでいるのに、見出しだけ下に集まる）:

```
④ 分子 y=0..84    → 見出し y=418   （4行目の高さ）
⑦ 分子 y=168..168 → 見出し y=754   （最下段より下）
⑪ 分子 y=336..420 → 見出し y=838
⑭ 分子 y=504..504 → 見出し y=838   ← ⑦⑪⑭⑰ が y=754〜838 に固まる
```

**スマホ（375×812）ではもっと悪い**:

| 成分の数 | 並べ直し | ずれた見出しの数 | 最大のずれ |
|--:|---|--:|--:|
| 7 | あり | 5 / 7 | +12マス |
| 12 | **なし** | **8** / 12 | +12マス |
| 20 | **あり** | **20** / 20 | **+28マス** |

⚠ **スマホでは並べ直さなくても起きる**（12個で 8/12）。

### 原因（特定できた。2つの数が別の単位で書かれている）

見出しチップの高さは **画面 px 固定**（`LABEL_CHIP_HEIGHT = 34px`。指で押す的なので
`labelScale()` が `1/縮尺` を掛けて画面上の大きさを保つ）。いっぽう**置き場所の計算はすべてモデル座標**。

したがって**引いて見る（＝答案が増える）ほど、チップはモデル座標の中で太る**:

| 場面 | `labelScale` | チップの高さ | 見出しに要る縦幅（1.1マス＋チップ） |
|---|--:|--:|--:|
| 答案 4個・PC | 0.84 | 0.64マス | 1.74マス（73px） |
| 答案 20個・PC | **1.59** | **1.21マス** | **2.31マス（97px）** |
| 答案 20個・スマホ | **3.97** | **3.03マス** | **4.13マス（173px）** |

**`tidyAnswerSlots()`（`game.js:2693）` が確保している縦の隙間は `GAP = GRID_SIZE * 2 = 84px` 固定**で、
そこには**こう書いてある**:

```js
const GAP = GRID_SIZE * 2;   // 84px。縦は見出しチップ（下へ約 80px）もここに収まる
```

⚠ **この「約 80px」は縮尺 1 倍（＝答案が数個）のときの値**で、
**答案が 10 個を超えると必ず 84px を上回る。**（PC 20個で 97px・スマホ 20個で 173px）。
つまり**並べ直した瞬間、どの見出しも真下の行の分子に必ずぶつかる。**

ぶつかると `placeMoleculeLabels()` が段送りで逃がす。逃げ先の値段（`labelPlacementCost`）は
**重なり 10000 / 他の分子を跨ぐ 300** で、**「自分の分子からの距離」はまったく数えていない**。
段は 12 段ぶん（＝ 最大 12×2 マス）まで見て、**下方向を先に試す**ので、
`跨ぎ3つ ＝ 900 < 重なり1つ ＝ 10000` となり、**遠くの空き行のほうが安く**なる。
結果、**行き場を失った見出しが下へ下へと送られ、いちばん下に固まる。**

### なぜ直さなかったか（⚠ ここが判断のいる所）

**直し方が3通りあり、どれを選ぶかで意味が変わるため、推測で選ばなかった。**

| 案 | 中身 | 害 |
|---|---|---|
| **①並べ直しの縦の隙間を、見出しのぶんだけ広げる** | `tidyAnswerSlots` の縦だけ `GAP_Y` に分ける | ⚠ **鶏と卵**: 必要な隙間は「並べ直したあとの縮尺」で決まり、その縮尺は「並べた大きさ」で決まる。1回ぶん見積もりを回すか、`rows` から逆算する式が要る。**しかもスマホで並べ直さない場合（12個で 8/12）は直らない** |
| **②書き出し練習のあいだだけ、見出しを「画面px 固定」から「図と同じ縮尺」へ戻す** | `labelScale()` を練習中は 1 にする | **筋が良い**: 34px の床は**押せる的だから**あるもので、⚠ **練習中の見出しは押せない**（`canvasEntryEnabled()` が `worksheetActive()` で false を返す＝§12-3 の「窓ごと閉める」）。押せないものに的の下限は要らない。**害**: 引いて見たとき番号が小さくなる（読めるかは実機で見る必要がある） |
| **③段送りに「自分の分子から遠いほど高い」費用を足す** | `labelPlacementCost` に距離項 | **全モードに効く**ので、ML 帯（見出しの重なり回避）の実測値が全部動く。⚠ 距離を重くしすぎると「重なってでも近くに置く」に反転する。この面の設計（§12・§13-2）を引き直すことになる |

**②を勧める。**「押せない見出しに、押せる的の大きさを使っている」という**理由の食い違い**が
症状の根っこで、そこを直すと**並べ直しの有無にもスマホにも同時に効く**（①はどちらにも足りない）。
①③は症状のほうを追いかける形になる。

⚠ **②を採るなら回帰テストを先に赤くすること。** 検査は
**「並べ直したあと、どの見出しも自分の分子の下端＋1.1マス から動いていない（20成分・PC とスマホ幅の両方）」**。
いまのコードで**必ず赤くなる**ことは上の実測で確かめてある（PC 10/20・スマホ 20/20 がずれる）。
帯は `IW` の続き（**`IW17`** が空き。台帳は `assembler/tests.js` 冒頭）。

### 決めてほしいこと

4. **①②③のどれで直すか。** 勧め: **②**（練習中は見出しを図と同じ縮尺にする）
5. **②のとき、引いて見たときの番号の読みやすさをどうするか**（下限を置かないと 20個で 8px 前後になる）。
   勧め: **下限は「画面 12px」くらいで置く**（的ではなく**文字**の下限なので 34px は要らない）

## A-4. 正解の図 —— エーテルだけ主鎖が横一直線にならない

### 原文

> **書き出しの正解**
> **エーテルのアルキル基の主鎖を横一直線に**

### 実測（原因は「番号レイアウトの門番」にエーテルが落ちること）

答え合わせの左列（正解）は `IsomerPractice.renderStandardFigure()` が描く。ここは**2本道**になっている:

```
ipNumberedLayout(mol) が非 null  → 主鎖を横一直線（IP_HSTEP=46px）＋炭素番号
              null              → layoutMolecule(mol) へ落ちる（42px 直交 BFS・向きは成り行き）
```

門番は `iupacNameDetail(mol)` の `kind === 'chain'`。⚠ **エーテルは主鎖に番号をつけないのが規則なので、
`iupacNameDetail` が null を返す**（`learn.js:589-591` にそう書いてある）＝ **エーテルは必ず落ちる側**。

**落ちた側で主鎖が横一直線になるかは運**。`layoutMolecule` に通したエーテル 10 件を測った:

| 分子式 | エーテル | 主鎖が横一直線 | 折れている |
|---|--:|--:|--:|
| C₃H₈O | 1 | 1 | 0 |
| C₄H₁₀O | 3 | 2 | **1**（イソプロピルメチルエーテル） |
| C₅H₁₂O | 6 | 2 | **4**（tert-ブチル／イソブチル／sec-ブチル／エチルイソプロピル メチル・エーテル） |
| **計** | **10** | 5 | **5** |

**折れ方の実例**（座標は `layoutMolecule` の出力そのまま）:

```
エチルイソプロピルエーテル  最長鎖: C(84,0) - C(42,0) - O(42,-42) - C(42,-84) - C(42,-126)
                                          ↑ ここで直角に曲がって、以降は縦に伸びる
sec-ブチルメチルエーテル    最長鎖: C(0,0) - O(42,0) - C(84,0) - C(84,-42) - C(84,-84)
```

⚠ **同じ表の中でアルコールは 46px・エーテルは 42px** と結合長も違う（別の関数が描いているため）。
7行の表で交互に並ぶので、**「エーテルだけ図の作りが違う」ことは見た目にも出る**。

### 規約に触れるか（`CLAUDE.md`）

> 検証はトポロジーのみ（座標・角度は見た目専用）。直交作図は意図された仕様

**触れない。** 直すのは**答え合わせの左列＝アプリが描く「標準の書き方」**であって、
**ユーザーの作図には一切さわらない**。`ipNumberedLayout` はすでに
「表示専用（座標＝見た目のみ）」と自分で名乗っており（`learn.js:578`）、
アルコール・アルカンの正解図は**とっくに横一直線**に描き直されている。
**エーテルだけがその扱いを受けられていない**のが今の状態。

⚠ **規約を変える提案はしていない。**（例外を足す必要も無い）

### 案と害

| 案 | 中身 | 害 |
|---|---|---|
| **①`ipNumberedLayout` に「番号なしで並べるだけ」の道を足す** | 主鎖（＝重原子の最長鎖。O を含む）を横一直線に置き、**番号は描かない**（`order` を返さない） | ⚠ **「主鎖」を `iupacNameDetail` 以外から決めることになる**。§0 の失効表が「`findLongestCarbonChain` は IUPAC の主鎖ではない」と釘を刺している所に近い。**番号を描かなければ食い違いは表に出ない**が、**そう決めたことを設計書に書かないと次の人が番号を足す** |
| ②`layoutMolecule` 自体を直す | 全モードに効く | **パズル・呼び出し・ギャラリーの図が全部動く**。回帰の面積が桁違い |
| ③エーテルの正解図だけ compounds.json の `target` から引く | 実装は小さい | **登録の無い異性体で崩れる**（C₉H₁₂ のエチルトルエン等・§11-7）。二重管理も増える |

**①を勧める。** ただし ⚠ **必ず「番号は描かない」を守ること** ——
エーテルは IUPAC で主鎖に番号を振らないので、**並べるための鎖と番号のための鎖を同じものにしない**。

### 決めてほしいこと

## B-2. ハース環を使ったときの立体異性体の決定

### 原文（統合レーン経由の補足を含む）

> **ハース環を使ったときの立体異性体の決定について**
> **ハース環を使用したときは、立体異性体が定まっているはずでは？立体視したときの形が決まっている**

### 実測 —— ⚠ **ユーザーの見立ては正しい。アプリはハース図の上下を立体として読んでいる**

**読んでいる**（`chemistry.js` の `readRingParityFromHaworth`）。面の決め方は2段:

```
1. 原子に haworthFace（+1=上 / -1=下）が明示されていれば、それ         ← M2b（▲▼ の面マーク）
2. 未指定なら、環外の置換基が環炭素から ±25° 以内で縦に描かれていれば   ← M2c（v173）
   その縦位置から導く（画面で上＝手前 +1 / 下＝奥 -1）
3. どちらでもない（斜めに描かれた）中心はスキップ ＝ 記述子を出さない
```

`DESIGN_stereochemistry.md` §12.1 が**そう決めた理由**を書いている:

> 教科書ハースでは「置換基を炭素の上に描くか下に描くか」が面そのものなので、
> これが最も直感的・教科書的で、別マークモードも不要になる（**R3（座標から読む）案の採用**）

⚠ **これは `CLAUDE.md` の「検証はトポロジーのみ（座標・角度は見た目専用）」に対する、
すでに置かれている明示の例外**（フィッシャー投影の `readAtomParityFromFischer` と同じ扱い）。
**新たに規約を変える必要はない。**

### では何が「決まっていない」のか —— 3つある

**① 読める中心には条件がある**

| 条件 | 満たさないと |
|---|---|
| 環に属する sp3 炭素で、**環の隣がちょうど2本** | スキップ |
| `isAsymmetricCarbon` が真（4置換基が全部違う） | スキップ |
| 環外の重原子置換基が **1本（＋暗黙H）または2本** | スキップ |
| 置換基が**縦から ±25° 以内** | **スキップ**（＝ 斜めに描いた図は立体が決まらない） |
| 環外2本のとき、2本が**別の面**を指している | スキップ（図が壊れている） |

⚠ **「決まらない」ときアプリは黙る**（記述子を出さない）。ユーザーから見ると
**「ハース図を描いたのに立体が付いていない」**が、**なぜ付かないかは画面に出ない。**

**② 読んだ立体は「名前」には効くが、「書き出し練習の採点」には効かない**

| 使い道 | ハースの立体を使うか |
|---|---|
| `lookupCompoundName`（α-／β-D-グルコピラノースの言い分け） | **使う**（`canonicalStereoCode` で絞る） |
| 立体対照ビュー（🧊）・R/S | 使う |
| **`canonicalCode`（同型判定の既定）** | **使わない**（§8.3「既定の戻り値は一切変えない」） |
| **`enumerateConstitutionalIsomers`（異性体の書き出しの正解集合）** | **使わない**（§8.3「異性体列挙には立体を入れない」） |
| **`stereoPractice`（立体異性体の書き出し練習）の4問** | ⚠ **1問も環の糖が無い**（2-ブテン・乳酸・酒石酸・乳酸3分子の環状エステル） |

⚠ **つまり「ハース環を使った立体異性体の書き出し」という練習は、いま存在しない。**
ハースの読み取りは**名前を引くためだけ**に使われている。

**③ ハース環モジュールは置けるが、置いただけでは立体は決まらない**

`getHaworthPlacementPlan` はある（パレットの「⬡ ハース環」）。置くと環と環内 O が出るが、
**立体を決めるのは「置換基を真上／真下に描くこと」**なので、
**環を置いた時点では立体は1つも決まっていない**（`readRingParityFromHaworth` が返すのは空）。
⚠ **ユーザーの「使用したときは定まっているはず」は、正確には
「置換基を上下に描き終えたときに定まる」**。

### 論点（⚠ **仕様は決めていない**）

| # | 決まっていないこと |
|---|---|
| **い** | **斜めに描いた置換基で立体が読めないとき、黙るのか言うのか。** いまは黙る |
| **ろ** | **ハース環を使った立体異性体の書き出し練習（α/β-グルコースなど）を作るか。** いま `stereoPractice` の4問に環の糖は無い |
| **は** | **「立体異性体は何種類？」（B-1）にピラノースは入っているか。** 入っている（不斉5個＝32種）が、⚠ **これは「ハース図を描いて数える」練習ではなく4択** |
| **に** | **構造異性体の書き出し（A-6）と立体は交わらせるのか。** §15-4 が「**立体異性の採点はやらない**」と線を引いている。⚠ **A-6 の「不斉炭素を答えさせる」はこの線の内側**（不斉炭素を**指す**だけで、立体配置は採点しない）だが、**線のすぐ際にある** |

### 決めてほしいこと

24. **「い」—— 立体が読めなかったとき、その旨を出すか。** 勧め: **出す**。
    ⚠ ただし**練習中は答えになりうる**ので、出す面を選ぶこと（自由モードの分子モーダルなら安全）
25. **「ろ」—— ハースの糖を `stereoPractice` のお題に足すか。** 勧め: **足す（α/β-D-グルコピラノース）**。
    ⚠ 読み取りは既にあるので**新しい判定は要らない**。要るのは**お題データと「並べ直す」で読めるかの実測**
26. **「に」—— A-6 が §15-4 の線を越えないことを確認するか。** 勧め: **確認して設計書に1行書く**
    （「不斉炭素を**指す**のは構造の話。立体配置の採点はしない」）
